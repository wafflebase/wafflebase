# Lessons — Release v0.6.11

## A check proves what it does, not what it is named

v0.6.10 and v0.6.11 were cut eight hours apart by the same person following the
same procedure. The first published an image that could not start and took
production down. The second published one that works.

The difference was not care. v0.6.10's release was not done carelessly — it had
a six-agent archive audit, an 86-claim adversarial audit that killed six claims,
and every registry artifact verified from the registry rather than the workflow
log. What it did not have was a reading of **what `verify-backend-image`
actually asserts**.

That job builds the production image and runs one thing against it:
`smoke-duckdb-runtime.cjs`, which proves the DuckDB extensions are bundled and
loadable offline. Its name says *verify backend image*. Its contents verify one
subsystem of that image. An image whose server could not start at all passed it,
twice, on two architectures.

**Rule: before treating a green check as evidence for a claim, read the check.**
Not the job name, not the step name — the command it runs. The question is never
"is CI green", it is "does anything CI runs fail when the thing I am about to
claim is false". For v0.6.10 the answer was no, and it was one `sed -n` on
`ci.yml` away from being known.

The corollary is what made the fix durable. `smoke-workspace-deps.cjs` reads its
dependency list from `package.json` rather than hard-coding it, because the
defect was *a dependency nobody remembered to add a line for*. A hand-written
list in the check would have had exactly the same failure mode as the
hand-written list in the Dockerfile — which is the actual root cause here, and
is still there: the runtime stage still copies each package's `dist/` by hand.
The smoke is a net under that, not a replacement for it.

## The workaround was the second failure

GitHub had an incident mid-release: Pull Requests in major outage, API and
Actions degraded. `POST /releases` returned 500 and 502 repeatedly.

The workaround was to push the `v0.7.21` tag over git — SSH was healthy while
the REST API was not — and create the release against the existing tag. That
worked, and it broke the chart release.

`chart-releaser` discovers changed charts **since the latest tag**. On its first
(failed) run the latest tag was `v0.7.20`, so it saw the chart change and
packaged `yorkie-cluster-0.7.21.tgz`; it then died on the same `POST /releases:
500`. By the time it was re-run, the tag I had pushed existed, so it diffed
`HEAD..v0.7.21`, found nothing, reported `Nothing to do. No chart changes
detected.` — and **succeeded**. A green run that published nothing.

**Rule: a workaround changes state that other automation reads.** Pushing a tag
is not a neutral substitute for letting the API create one; the tag is an input
to a tool downstream. The failure was silent and reported success, which is the
worst combination, and it was only caught because the chart index was checked
against `helm search` rather than assumed from the green run.

## The recovery nearly did more damage than the outage

Rebuilding the chart index by hand, the obvious command is
`helm repo index <dir> --merge <existing>`. It ran, exit 0, no warnings.

The output had **782 fewer lines** than the input. Checking per-chart, it had
dropped **25 of the 156** `yorkie-cluster` versions. Publishing it would have
broken every consumer pinning an older chart — a wider blast radius than the
outage being recovered from, caused by the recovery.

What caught it was comparing line counts before pushing, for no better reason
than that a merge should not shrink a file. The per-chart count came after, and
the entry was spliced into the original index instead, leaving a diff of one
removed line (the `generated:` timestamp) and 35 added, with the entry's
`digest` checked against the package's real `sha256`.

**Rule: during recovery, the bar for verification goes up, not down.** The
instinct is the opposite — the outage creates urgency and the recovery step
feels like restoring a known-good state. But recovery steps are run once, under
pressure, by someone who has been staring at the problem, and they skip the
review that normal changes get. A merge that shrinks a file, a sync that reports
`Failed`, a publish that reports success with nothing published: each was a
cheap check away.

## Read the failure, not the summary

Three times in this release a status was wrong in a way that mattered, and each
time the real state was one command deeper:

| what it said | what was true |
| --- | --- |
| `gh pr merge` → HTTP 502 | the merge had landed; `git fetch && git log origin/main` showed it |
| githubstatus.com → "All Systems Operational" | runs had been stranded `queued` for 2h32m; the incident was declared later |
| ArgoCD → `Synced / Healthy` (v0.6.10) | the pod was in `CrashLoopBackOff` |
| ArgoCD sync → `Failed` (v0.7.21) | yorkie rolled out fine; the failure was an unrelated Percona CRD exceeding the 262144-byte annotation limit |

The last one is the interesting direction: a **failure** summary that was not the
failure it looked like. Reading the message rather than the phase is what
separated "the release is broken" from "an unrelated object in the same
Application cannot be applied" — and the latter is a real finding that now needs
its own fix, since every future sync of that Application will report `Failed`
for the same reason.

**Rule: a phase is a pointer to a message. Read the message.**

## One replica means there is no such thing as a degraded rollout

`wafflebase` runs `replicas: 1`. v0.6.10's rollout reached `ready=0` with the
previous ReplicaSet already scaled to zero — a bad image is a full outage, with
no partially-serving state in between.

yorkie, at 3 replicas, would have surfaced the same class of defect as one
unready pod while two kept serving.

This is not an argument for scaling wafflebase up, which has its own costs. It
is an argument that **the pre-flight check has to carry the weight the replica
count does not**. That is why v0.6.11 ran the smoke against the *published*
image before pinning it, rather than trusting the local build that produced the
same bytes — the published artifact is what the cluster pulls, and it is the
last point where the check is cheap.
