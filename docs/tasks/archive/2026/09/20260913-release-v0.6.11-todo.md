# Release v0.6.11

**Created**: 2026-09-13

Cut `v0.6.11`. Two things, deliberately bundled: the fix for the image that
took production down on v0.6.10, and the bump to `@yorkie-js/sdk` 0.7.21.

## Why this release exists

v0.6.10 shipped a backend image that could not boot — `packages/slides/dist`
was never copied into the runtime stage, and #1022 had moved the backend's only
value import of slides into the Nest module graph, so a latent gap became a
crash loop. The Deployment reached `ready=0` with the previous ReplicaSet
already scaled to zero. Production was restored to v0.6.9 by
`kubectl rollout undo`, and `yorkie-team/devops#355` returned the manifest to
match.

So **production has been on v0.6.9 since**, and this release is what moves it
forward again. That is the reason the SDK bump rides along rather than waiting
for its own cut: there is one rollout to make, not two.

Full account: `20260913-release-v0.6.10-todo.md` (its post-merge section
records the outage, the cause and the fix).

## The box v0.6.10 is the reason for

- [x] **Build the backend image and run `smoke-workspace-deps.cjs` against it
      before publishing.** Done before the release commit: all three workspace

      because that job only ran the DuckDB extension smoke. #1063 added the
      workspace-dependency smoke to CI, and this box runs it locally too — the
      release is the last point where a broken image is still cheap.

## Why the SDK bump matters here

yorkie-js-sdk 0.7.21 fixes a client-wedging bug: `CRDTRoot.garbageCollect`
dereferenced a worklist entry without checking it resolved, and the throw lands
inside `Document.applyChangePack`, which every sync runs — so a client that hit
it never synced that document again. It also stops an ordinary `arr[i] = x` in
a loop from growing `docSize.live` without bound.

wafflebase is a heavy `arr[i] = x` consumer through the sheets grid, so the
unbounded-growth half is not theoretical here.

It pairs with yorkie 0.7.21 on the server, already rolled out to this cluster
(3/3 pods, 0 restarts).

> set to false. A share-link viewer can write to a document by attaching with

Read from `kubectl logs` after the rollout, not assumed. This remains the open
decision from v0.6.10's notes: flipping it needs the auth-webhook methods
registered on the Yorkie project and somebody to accept the false-denial risk.

## Review

The release went out clean, and the only thing worth recording is the contrast
with v0.6.10 eight hours earlier.

Same repository, same procedure, same person. v0.6.10 published an image that
could not start and took production down; v0.6.11 published one that works. The
difference is not care — v0.6.10 was not done carelessly. It is that v0.6.10
read a green `verify-backend-image` as *the image is good*, and that job only
ever proved the DuckDB extensions were bundled. The gap between what a check
proves and what its name suggests is where this went wrong.

So this release ran the image twice: once locally before the release commit, and
once against the published artifact before pinning it. Both times with the
smoke #1063 added, which reads its dependency list from `package.json` so it
cannot go stale the way a hand-written list would.

Rolled out on one replica with no canary, which is worth naming as accepted risk
rather than passing over: `wafflebase` runs `replicas: 1`, so a bad image is an
outage, not a degraded rollout — exactly what v0.6.10 was. The smoke on the
published image is what replaces the canary here.
