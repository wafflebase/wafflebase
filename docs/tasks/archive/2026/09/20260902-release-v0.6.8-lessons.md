# Lessons — Release v0.6.8

## A window that adds a dependency leaves the release session's tree stale

`pnpm verify:fast` failed on the first run: **25 frontend test files
failed**, every one of them on

```
Error: Failed to resolve import "hyparquet" from
  "../sheets/src/import/parquet-importer.ts". Does the file exist?
```

Nothing in the release diff touches that file. #994 added `hyparquet`
and `hyparquet-compressors` to `packages/sheets/package.json` inside
this window, and this checkout had not installed since. The failure
presents as a code defect in someone else's merged PR — a resolve error
naming a real source file — and the reflex it invites is to go read
`parquet-importer.ts`.

**Rule: before the release `verify:fast`, run `pnpm install
--frozen-lockfile` whenever any `package.json` dependency block moved in
the window.** Cheap to check:

```bash
git diff v<prev>..HEAD -- '**/package.json' | grep -E '^\+ +"[^"]+": "\^?[0-9]'
```

v0.6.6 hit this same thing and recorded it as "needed a `pnpm install`
for a package added mid-window". v0.6.7 did **not** hit it, but only
because its Yorkie bump forced an install for unrelated reasons — so the
step got read as incidental to the bump rather than as a standing
precondition. A precondition that only shows up when something else
happens to satisfy it will keep being rediscovered.

`--frozen-lockfile` is the flag that makes this safe to run reflexively.
It installs exactly what the lockfile says and **cannot** rewrite it,
which is precisely the failure v0.6.7's self-review had to catch and
revert by hand (a bare `pnpm install` on this machine flipped an
unrelated `@types/node` peer suffix, because the local pnpm is 9.15.9
and the repo pins `packageManager: pnpm@10.5.2`). Verified here: the
install completed and `git status pnpm-lock.yaml` stayed clean.

## `target-version` drifts *ahead* too

v0.6.6 found a design doc whose `target-version` ran ahead of reality;
v0.6.7 found three running behind and concluded behind was the direction
to watch. This release found one ahead again: `template-gallery.md`
read `0.7.0` while Phases 1 and 2 both shipped in the window.

The question the number answers is **"which release does this design
first land in?"** — not "when is it finished". `board/board.md` is the
precedent: it reads `0.6.2`, the release SP1 landed in, while SP2, SP3
and SP4 shipped in three later versions under their own docs. Reading it
as "when the last phase lands" would have kept board's number moving for
four releases and made it useless as a record of anything.

The distinction that decides a partially-shipped doc: **does a user of
wafflebase receive any of it in this release?** The template gallery —
publish, preview, use, the workspace tab — yes, so it moves to `0.6.8`.
`design-editor-local-plugin.md` stays at `0.7.0` because no user
receives the local plugin yet and `npm-publish.yml` publishes only
`@wafflebase/cli`. A doc merely *modified* in the window (`cli.md`,
which grew #999's commands) does not re-land and keeps its number.

## An honest `active/` produces a small archive batch — do not fix that

v0.6.7 archived nine tasks, eight of which had shipped with their boxes
never ticked. The same sweep two days later moved exactly one, and it
moved on its own (`sidebar-nav-drift` was already at zero unchecked).

The temptation is to read "1 archived" as a sweep that did not try hard
enough, and to go looking for boxes to tick. The correct output of an
audit over a set that was just audited **is** a small number. Every
unchecked box was still read against the repo, and every one is real
remaining work — a `KNOWN_BUG`-skipped test that still skips, a `public`
tier still refused with a `400` in the service, a bench with zero runs.
The count is the measurement, not the target.

One box was ticked, and only because its own evidence sat three lines
below it: `template-gallery`'s "Open questions below answered before
Phase 1 starts", with the **Decisions (2026-09-01)** section — three
ticked decisions dated the day Phase 1 shipped — immediately following.
Checked that no other "Open questions" heading exists in either the task
doc or the design doc before ticking, because the v0.6.7 lesson cuts
both ways: a tick without evidence and a denial without evidence are the
same error.

## A number inherited from another task doc is a second-hand claim

The release notes said #1002 was "Net −225 lines", copied from that
task's own Review section — the kind of figure that reads as measured
because it is precise. It reproduces under no grouping of the commit:
`git show --numstat` gives −233 across the eight call sites, −227 with
the design-sandbox fixture included, −150 counting production files
only.

Nothing turns on which is right. What turns on it is that **release
notes are where a claim stops being checkable** — the task doc it came
from will be archived, and the number will outlive everyone who could
say where it came from. A digit copied across documents launders itself
into evidence.

Same class as v0.6.7's "the box says undone, so the work is undone":
the artifact is authoritative, the write-up about it is not. Recompute
every number the release notes state, even when a task doc already
states it, and especially when it is precise.

## Qualifiers need the same evidence as the claim they qualify

"No `yorkie-agent[bot]` commits this window" is measurable in one
command, and it was true. What was appended to it — "the first release
window since the pipeline was armed" — quietly asserted a second fact,
the arming date, which was never checked. `v0.6.0..v0.6.1` also had
zero, so the sentence was probably false.

The tell is a qualifier that sounds like context rather than a claim:
*the first since*, *the only one to*, *unlike every other*. Each one is
a second assertion riding on the first one's verification. Either
measure it (the six intervening windows carried 8, 2, 4, 12, 18 and 4)
or delete it — a superlative is not decoration.

## A clean rebase is not a still-true document

`git rebase origin/main` before pushing exists to surface conflicts.
This one had none — and it invalidated more of the release than a
conflict would have. #1005 landed while the notes were being written,
and it moved five separate things:

- the window went from 7 commits to 8, and one author's count with it;
- the notes needed a fifth highlight that did not exist when the
  outline was drawn;
- a second task became archivable (`template-thumbnails`), so the
  archive audit had to run again;
- five boxes in `template-gallery-todo.md` had shipped an hour earlier
  — #1005 tracked its own work in a **new** task pair rather than
  ticking the gallery's boxes, recreating exactly the "shipped, never
  ticked" state v0.6.7 archived nine tasks out of;
- a source spot-check taken 40 minutes earlier
  (`packages/core/src/` holds exactly `geometry/`, `tokens/`, `url/`)
  was already false: #1005 added `image/`.

Git merged all of it cleanly, because none of it is a textual conflict.
It is a **semantic** one, and only a re-read finds it.

**Rule: after the pre-push rebase, if `origin/main` moved at all,
re-run the release audit — the window, the counts, the archive pass and
any source spot-check — against the new tip.** A release note is a claim
about a tree; rebasing changes the tree.

The narrower corollary, and the reason two of the three claim-audit
findings existed at all: **a spot-check has a timestamp.** "I checked
that directory" means "I checked it at that commit". Recording *which
commit* alongside the finding is what makes it re-checkable rather than
merely re-assertable.

## Check "first commit" claims against the whole history

v0.6.8's window has one commit from a non-maintainer, and the note that
writes itself is "their first". It is their **second** — they also
authored one on 2026-08-09. v0.6.7 made this exact claim about a
different contributor and it was wrong there too (a fourth commit, not a
first), so it now costs one command and is worth spending every time:

```bash
git log --format='%ae|%ad' --date=short | grep <handle>
```
