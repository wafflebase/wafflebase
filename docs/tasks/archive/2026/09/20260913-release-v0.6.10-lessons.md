# Lessons — Release v0.6.10

## The tooling could not see nine checkboxes, and nobody would have noticed

`20260904-class-b-backend-endpoints-todo.md` wrote its nine steps as an
ordered list — `1. [x]`, `2. [ ]`. `scripts/tasks-archive.mjs` matched
`/^\s*-\s*\[ \]/m`, which requires a `-` bullet. So a task with **eight
open steps read as a task with no steps**, and this release's
`pnpm tasks:archive` would have filed it as finished.

The failure is worth separating from the ordinary "boxes never ticked"
pattern the last three releases have been chasing. That one is a human
forgetting. This one is the opposite: the boxes were written, they were
accurate, they were sitting in the file — and the machine that reads them
was looking for a character that was not there. Markdown renders `1. [ ]`
and `- [ ] ` identically, and GitHub renders both as checkboxes, so there
was no rendering, no review and no audit that could have surfaced it.
Only a reader who opened the file *and* knew the regex would see it, and
the whole point of the tooling is that nobody has to.

**The general shape: a checklist has two readers, and only one of them
complains.** A human reading `20260904-class-b-backend-endpoints-todo.md`
sees nine checkboxes. `tasks-archive.mjs` sees zero. When those two
disagree, the tool wins silently — it archives, reports success, and the
disagreement never surfaces as an error because from the tool's side
nothing went wrong. Every other lesson in this series has been about the
human half drifting from reality; this is the first about the *tool* half
drifting from the human half.

Fixed at the source — `/^\s*(?:[-*+]|\d{1,9}[.)])\s*\[ \]/m`, every
CommonMark list marker — rather than by rewriting the one file, because
the next author to number a list is not doing anything wrong.

**Rule: when a convention is enforced by a regex, the regex is part of
the convention and has to be as permissive as the format it reads.** A
stricter parser than the format does not fail loudly; it under-matches,
and under-matching a "is there unfinished work" query answers *no*.

## A wrong correction outlived the release that made it

v0.6.9's lessons file — the same file whose closing section is titled *"A
wrong correction is worse than no correction"* — contains one.

It records that `template-gallery-public-tier`'s box *"Remove
`DELETE /images/:id` … confirm no client calls it"* had **stopped being
safe to act on**, because `wafflebase images delete` was now a caller and
executing the box would break a released CLI command.

It is not a caller. `HttpClient.deleteImage`
(`packages/cli/src/client/http-client.ts:1071`) issues
`DELETE /images/:id` *relative to* `this.base` (`:356-362`), which is
`apiV1Base(this.config)` (`:239-241`) =
`${origin}/api/v1/workspaces/${workspaceId}`
(`packages/cli/src/client/url.ts:69-71`). The CLI reaches
`api/v1/images.controller.ts:91`; the box names
`image.controller.ts:158`. Different controllers. The frontend has no
delete caller at all.

The mechanism is the one that file itself named and then repeated:
**grep found the string and the reader stopped there.**
`grep "/images/" packages/cli` returns dozens of hits across source and
tests; two of them — `commands/images.ts:197` and `http-client.ts:1074` —
look exactly like callers of the route in question, and they are the two
a reader scanning for a *delete* stops on. They are relative paths.
**A relative path is not a URL until you resolve its base**, and
resolving it is three `Read`s.

Two things are worth taking from this rather than the object-level
correction:

1. **The falsify framing works, and it works on your own inputs too.**
   This audit's brief *told* the agent the box was unsafe, presenting it
   as established fact from the prior release, and asked it to "re-derive
   whether" — and it came back refuting the premise with the base-URL
   chain. An agent asked to *confirm* the note would have confirmed it;
   the note is plausible, which is the failure mode. The instruction has
   to permit refuting the instruction.
2. **The prior release's own "bar rises with where you write it" rule was
   applied to one claim and not to its neighbour.** v0.6.9 caught the
   `docker-publish` error at exactly this promotion point and wrote the
   rule down two sections later. The `DELETE /images/:id` claim sat in
   the same file, was promoted the same way, and got none of the same
   scrutiny — because the audit that caught the first one had already
   finished. **A rule written in response to a finding does not
   retroactively apply to the findings beside it.** When a claim audit
   kills one claim in a document, the others in that document are the
   most likely next failures, not the least.

## The post-merge section failed again, and "try harder" is not the fix

v0.6.8 left its seven post-merge boxes unticked for three days. v0.6.9
wrote a box explicitly instructing the next releaser to **close this
section in the same sitting as the rollout check**, and then left all
seven — plus one in its own Plan section — unticked for **eight days**.
Worse than the release it was written to fix.

Every step had succeeded. The tag was annotated and on the merge commit.
The Release was Latest. Both release-triggered workflows were green and
version-named. npm's `dist-tags.latest` had moved and Docker Hub had a
genuine multi-arch index. devops#351 moved all six lines. The pod came up
2h12m after publication and had not restarted in eight days. All of it
re-derived at this cut in about ten minutes.

So the instruction is not wrong and the releaser is not careless. **The
instruction has no trigger.** It names a sitting — "when you run
`kubectl get pod`" — in which the file is not open, cannot be reached
from anything on screen, and belongs to a repository the operator is not
in. `kubectl`, Docker Hub, npm and the devops repo have nothing that
points back at `docs/tasks/active/` in *this* repo. Asking someone to
remember a file while they are looking at four things that do not mention
it is asking for the failure that has now happened three times.

Two things that would actually work, in preference order:

1. **Make the release PR itself carry the post-merge section**, so the
   artifact that survives the merge is the one with the boxes on it. A
   PR comment posted by the merge is on screen at exactly the moment the
   rollout starts.
2. **Let the next release close the previous one and say so in its
   plan** — which is what actually happened here, both times. If that is
   the real mechanism, write it as the mechanism instead of as a
   recurring failure: "the release task's post-merge section is closed by
   the *following* release's audit, with evidence re-derived at that
   point." It costs the eight-day gap, and it has a trigger.

This release's own post-merge section still says "close it in the same
sitting", because that is still the better outcome. But the honest note
is written beside it: the instruction has failed twice and the fallback
has worked twice.

## A default that flips in code does not flip in a deployment

#1046 changed the Yorkie auth webhook from opt-in enforcement
(`=== 'true'`) to enforce-unless-`false`. Read from the repository, that
is a security posture improving by default, and it was on its way into
the release notes as a headline.

It changes nothing on the deployment. `yorkie-team/devops`
`k8s/wafflebase/deployment.yaml` sets
`YORKIE_AUTH_WEBHOOK_ENFORCE: "false"` explicitly — a deliberate choice
from v0.6.0, with a comment saying to flip it after confirming no false
denials — and `kubectl get deploy` confirms the running pod carries it.
The manifest pins the exact value the new default was meant to stop
depending on. And the client-side flag that used to keep revision history
out of reach was deleted in the meantime, so the combination is worse
than either half: on the running deployment a share-link **viewer** can
list, read and restore full revision history, and write to the document.

**A default is a claim about installs that configure nothing.** Ours
configures something. The generalization to keep: when a release note
says "now the default", the sentence is only true of a deployment whose
manifest is silent — so the check is not "what does the code default to"
but `grep` the manifest for the variable. That is one command and it
moved a headline into a caveat.

## Six audits, and the one instruction that did the work again

Same finding as last release, reproduced rather than inherited, so it is
worth restating with what changed. The instruction was:

> Verify a SHIPPED verdict by finding the actual code. Quote `file:line`
> and the specific symbol you READ. **Do NOT trust a commit message or a
> PR title.** Report what HELD as well as what FAILED.

The last clause earned its place this time. Two of the six groups came
back with *zero* archivable tasks and a precise account of why — eight
long-running tasks where every unchecked box was genuinely unshipped, and
ten more where the same held. An audit that reports only failures cannot
be distinguished from one that stopped early; those two reports are only
credible because they say what they checked and found intact.

What was new: one group was handed a false premise on purpose (the
`DELETE /images/:id` note) and refuted it. One group discovered the
ordered-list checkbox problem while doing something else entirely — it
was investigating a `0 unchecked / 0 checked` reading that looked like a
task with no content, and found nine checkboxes instead. **The count was
the anomaly, and the anomaly was in the measuring instrument.** A task
reporting 0/0 is the shape worth treating as a bug report about the
scanner rather than as a finding about the task.

## Titles are not diffs, and agent PRs are the sharp case

The release checklist has said "classify by diff, not by title" since
v0.6.15 of the yorkie procedure. This window is where it earns it.

`#1046 Mount the notes toolbar on the share-link route` touches 22
frontend files, **17 backend files**, notes, slides, sheets, docs and
documentation — because enforcing the auth webhook by default means every
server-side Yorkie client needs a scoped service token and every
read-only mount across five document types has to stop writing. The
security change of the release is inside a PR named after a toolbar.

`#1053 Docs: a list item's level change carries its children` carries 8
slides files. `#1047 Docs: select-all then type is one undo unit` carries
a share-link resolution fix. These are honest titles — each names the
defect the PR was opened for — but a release note written from the title
list would have missed the auth-webhook flip entirely, which is the one
item in this release with an upgrade note.

**Rule: for any PR whose diff spans more packages than its title
implies, read the commit body.** These bodies are long and they explain
the spread; the information was never hidden, it was just not in the
subject line.
