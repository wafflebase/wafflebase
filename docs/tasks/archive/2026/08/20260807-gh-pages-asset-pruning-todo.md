# GitHub Pages deploy timeout — prune the publish directory

> **Correction (2026-08-07).** The trigger for the failures below was a
> GitHub-side **Pages "Deployment Lag" incident**, not the growth this
> document describes. The incident was published to githubstatus.com after
> this was written; the "no incident" line under Problem was accurate when
> checked and is now superseded. See [Outcome](#outcome).
>
> The growth is real and independently measured, and stopping it was worth
> doing — but it was a standing fragility, not the cause of that day's
> outage. Read the framing below as "reclaim headroom", not "fix the
> timeout".

## Problem

`pages-build-deployment` (GitHub's auto-generated workflow for a
branch-sourced Pages site) has been failing since 2026-08-06 11:48 UTC:

```
Current status: deployment_in_progress   (× 120, over 10 minutes)
##[error]Timeout reached, aborting!
Canceling Pages deployment...
```

Our own `GitHub Page Publish` workflow succeeds every time — the artifact
uploads fine and the deployment is created. What fails is the wait for the
Pages backend to finish processing it, against the 600s timeout baked into
`actions/deploy-pages@v5`.

The Pages-side processing time has been climbing monotonically:

| Time (UTC)  | `deploy` job | Result        |
| ----------- | ------------ | ------------- |
| 08-05 (all) | 8–25s        | pass          |
| 08-06 06:38 | 9s           | pass          |
| 08-06 07:14 | 48s          | pass          |
| 08-06 07:59 | 1m50s        | pass          |
| 08-06 08:46 | 4m18s        | pass          |
| 08-06 11:11 | 9m38s        | pass (barely) |
| 08-06 11:48 | >10m         | **fail**      |
| 08-06 14:18 | >10m         | **fail**      |
| 08-06 14:44 | 10m03s       | pass (barely) |

It now sits on the timeout boundary, so pass/fail is a coin flip.

Ruled out: the uploaded artifact was 25.7 MB on a 9s deploy and 26.0 MB on a
258s deploy — essentially unchanged, so artifact size is not the driver. No
GitHub Pages incident on githubstatus.com for that window.

## Root cause

The published site grows without bound and is never pruned:

```
2026-08-05  1755 files  80.7 MB
2026-08-06  2190 files  98.3 MB      (+435 files / +18 MB in one day)
```

68.7 MB of the 98 MB — **70% of the site** — is dead VitePress chunks, one
generation per deploy, ~300 generations deep:

| Path                                          | Files | Size    |
| --------------------------------------------- | ----- | ------- |
| `docs/assets/chunks/@localSearchIndexroot.*.js` | 308   | 33.2 MB |
| `docs/assets/chunks/VPLocalSearchBox.*.js`      | 315   | 19.2 MB |
| `docs/assets/chunks/theme.*.js`                 | 315   | 16.1 MB |

Two workflow settings combine to cause this:

1. `peaceiris/actions-gh-pages` runs with `keep_files: true`, so a deploy
   never removes anything. This is deliberate — clients holding a cached
   `index.html` still need the previous build's hashed assets.
2. The `Cleanup old assets` step is the counterweight, but its manifest is
   built from `find assets -type f`. **`docs/assets/` was never recorded**,
   so nothing under it was ever eligible for removal.

Separately, `assets/` stopped holding flat at 208 files on 08-06 11:11
(342 → 439 → 535) because #679 (Dependabot lockfile bumps) and #685 churned
nearly every content hash. That is the retention window working as designed,
but with `KEEP_COUNT=5` the ceiling is ~5 × 206 ≈ 1030 files.

Caveat, stated honestly: between 06:56 and 08:46 the file count moved only
1787 → 1799 while the deploy time went 9s → 258s. Growth alone does not
explain a 66× jump, so a Pages-side threshold or performance change likely
compounds it. Shrinking the site is the part under our control, and it buys
back the headroom regardless.

That caveat turned out to be the whole story — the unexplained factor was a
GitHub Pages incident. See [Outcome](#outcome).

Also note: Pages is configured as `build_type: legacy` (deploy from the
`gh-pages` branch), so `pages-build-deployment` is generated by GitHub and
its 600s timeout is **not** editable by us. Reducing the site is the only
direct lever.

## Plan

- [x] Record `docs/assets/` in the deploy manifest alongside `assets/`
- [x] Make pruning set-based rather than manifest-diff-based, so the ~940
      pre-existing orphaned chunks (never named in any manifest) are
      collected too, and future orphans self-heal
- [x] Reduce the retention window from 5 generations to 3
- [x] Add a guard that refuses to prune when the newest manifest is empty
      (set-based deletion would otherwise empty the site)
- [x] Dry-run the pruner against the real `gh-pages` tree before merging
- [x] Verify on the next `main` deploy that the `deploy` job drops back to
      seconds and the site still serves

## Verification

Both steps were extracted from the workflow YAML and run for real — the
manifest step against a synthetic `dist/`, the cleanup step against a
worktree of `origin/gh-pages` (2190 files / 98.3 MB) with the commit and push
replaced by a dry-run echo.

| Check | Result |
| ----- | ------ |
| Manifest — a tree is missing | exits 1, `::error::` on stderr, manifest file 0 bytes |
| Manifest — both trees present | exits 0, lists both trees |
| Prune — normal run | removes 1656 files; every file named by the newest manifest survives; `assets/` settles at the 3-manifest union (302); `pdfjs/` untouched at 185 |
| Prune — empty newest manifest | exits 1 with `::error::`, 0 staged deletions |
| Prune — newest manifest omits a tree | exits 1 with `::error::`, 0 staged deletions |

Projected first real run: **~81 MB removed**, site drops from ~98 MB to
roughly ~20 MB once the 3 retained generations are added back (3 generations
of VitePress chunks are ~0.66 MB against the 68.7 MB in the tree today).

## Review feedback

CodeRabbit raised two findings on PR #702.

**Partial manifests (major) — valid, fixed.** `find assets docs/assets` exits
non-zero on a missing directory but still emits what it did find, and without
`pipefail` the trailing `sort` reported success. Reproduced: the step exited 0
having written a non-empty manifest naming only `assets/`. Under set-based
pruning that manifest is worse than none — it would delete the current build's
entire `docs/assets` tree, and the non-empty guard would not catch it.

Fixed on both sides rather than one: the manifest step asserts both
directories and sets `pipefail`, and the cleanup step now additionally
requires the newest manifest to name at least one file under each tree, so a
malformed manifest is rejected however it was produced. The suggested patch
itself was not applied — it `cd`s into `dist` while keeping a `dist`-relative
redirect path, which would fail to open the output file.

Testing the fix surfaced a second bug in it: the `::error::` echo sat inside
the subshell whose stdout *is* the manifest, so the annotation was written
into the manifest file (83 bytes) instead of the log. Routed to stderr.

**Task filename date (minor) — not applied.** The repo names task docs by
local (KST) date, not UTC: `20260804-panel-concurrency-todo.md` was committed
at 2026-08-03 UTC. It was 2026-08-07 KST when this landed, so `20260807`
follows the existing convention.

## Design notes

Set-based instead of diff-based is the key change. The old loop walked
*expired manifests* and removed files they named, which meant a file that
was never in any manifest was unreachable forever — exactly the state
`docs/assets/chunks` is in. The new step computes the keep-set from the 3
newest manifests and removes every tracked file under `assets/` and
`docs/assets/` outside it.

That makes an empty or malformed manifest dangerous in a way it was not
before, hence the explicit non-empty guard on the newest manifest.

`pdfjs/` and the `docs/` HTML are untouched: the prune is scoped to the two
hashed-asset directories, and `pdfjs/` ships stable, unhashed filenames.

On the first run after this lands, the two older manifests carry no
`docs/assets` lines, so the keep-set for docs is just the current build.
That is precisely the intended one-time purge (~68 MB), at the cost of docs
readers mid-session needing one reload.

## Outcome

PR #702 merged as `09c309cf` on 2026-08-06 15:56 UTC. The publish workflow it
triggered never got a runner and was cancelled after 15 minutes with zero
steps executed; a re-run at 23:09 UTC succeeded and did the work.

### Measured result

| | Before | After |
| --- | --- | --- |
| Site | 2190 files / 98.3 MB | **597 files / 18.2 MB** |
| `docs/assets` | 1426 files / 71.4 MB | 68 files / 1.35 MB |
| `assets` | 535 files | 302 (3-manifest union) |
| `pdfjs` | 185 files | 185 (untouched, as designed) |
| `.manifests` | 5 | 3 |
| Pages `deploy` job | 600s timeout | **9s** |

The dry-run projection (~81 MB removed, ~20 MB remaining) matched the real
run (80.1 MB removed, 18.2 MB remaining). Every asset URL referenced by the
live `/` and `/docs/` HTML returns 200 — 12 of 12 checked, so the purge broke
no live reference. The prune commit landed as
`Clean up assets older than 3 deployments`.

### Correction to the root cause

The 08-06 failures were caused by a GitHub **Pages "Deployment Lag"**
incident (githubstatus.com, mitigated 15:50 UTC), not by the growth this task
addresses. When the root cause was first investigated, that incident had not
yet been published, so the `incidents.json` check came back clean and the
timeout was attributed to site size.

The 9s deploy after the prune therefore cannot be credited to the prune
alone: the incident was mitigated roughly seven hours before that run. The
two effects are not separable from this data.

What survives the correction, because it was measured directly:

- The publish directory grew without bound — 1755 → 2190 files and
  80.7 → 98.3 MB in a single day.
- 68.7 MB of it was dead VitePress chunks, ~300 generations deep, that no
  code path could ever reach.
- That is now 1.35 MB and bounded at 3 generations.

So the change was worth making, but the honest framing is "stopped an
unbounded leak and reclaimed headroom", not "fixed the deploy timeout". A
site sitting at 98 MB and climbing is what made a transient platform
incident able to break deploys at all.
