# Release v0.6.19

**Created**: 2026-11-27

Cut `v0.6.19`, the first release that carries the desktop app (macOS only),
and bring the backend up to fifteen PRs the frontend already ships. GitHub
Pages deploys `main`, so wafflebase.io has been running the new UI against
the `v0.6.18` backend since each merge. Today that means:

- the template gallery's category filter answers `400`, because the
  frontend sends slugs (`?category=work`) and `v0.6.18` accepts only the
  eight old labels (`IsIn(TEMPLATE_CATEGORIES)`);
- the Webhooks settings section, chat member lists, channel Files and the
  editor chat panel's "shared in" call routes that answer `404`;
- the desktop app's default server says "too old for desktop sign-in",
  because `api.wafflebase.io/auth/providers` returns
  `{"github":true,"google":false}` with no `desktop` field.

Probed read-only on 2026-11-27: `GET /templates?scope=public&category=work`
→ `400`, `?category=Business` → `200`; `/workspaces/x/webhooks` → `404`;
`POST /auth/desktop/session` → `404`.

## Preconditions

- [x] **Seven Prisma migrations, applied by the init container.**
      `yorkie-team/devops` `k8s/wafflebase/deployment.yaml` runs
      `npx prisma@6 migrate deploy` in the `prisma-migrate` init container,
      so the rollout applies them before the server starts. None drops or
      rewrites a column, and none takes a long lock: every table touched is
      small (chat is a week old, templates are 38 rows).
  - `20261121150000_chat_default_channel` (#1189): adds nullable
    `ChatChannel.defaultKey` and a unique index on it. **Backfills**: adopts a
    public `general` channel as the default and unarchives it, creates
    `#general` for every other workspace (owned by its first owner), and joins
    every workspace member at the channel tail. A workspace whose `general` is
    private keeps it and gets no default. The channel-list read repairs a
    workspace still missing one, which covers the old pod during the rolling
    deploy.
  - `20261122000000_webhooks` (#1191): new tables `Webhook`,
    `WebhookDelivery`, `WebhookContentPending`, with their indexes and FKs.
  - `20261122100000_webhook_recover_from` (#1191): nullable
    `Webhook.recoverFrom` and a `WebhookDelivery` index. Both tables are
    empty at apply time.
  - `20261125090000_chat_a_client_id` (#1201): nullable
    `ChatMessage.clientId` and a unique index on
    `(channelId, authorId, clientId)`. Every existing row is `NULL`, and
    Postgres treats `NULL`s as distinct, so it cannot conflict.
  - `20261125120000_chat_d_document_refs` (#1201): new table
    `ChatDocumentRef`. Existing messages get no refs (no backfill); cards
    appear on messages posted or edited after the rollout.
  - `20261126000000_template_category_slugs` (#1205): **data rewrite**,
    raw SQL. Relabels `TemplateListing.category` from the eight v1 labels
    to slugs (`Business` → `work`, `Project management` →
    `work/project-tracker`, …). Raw SQL on purpose: a service write would
    send every approved public card back to review, and this leaves
    `updatedAt` alone. Values outside the eight are left as they are.
  - `20261126000001_template_seed_record` (#1205): new table
    `TemplateSeedRecord`, used only by `sync:templates`.
- [x] **No setting production must add.** Every new backend setting is
      optional and off or safe by default (`packages/backend/README.md`):
  - `WAFFLEBASE_WEBHOOKS_ENABLED` (#1191): only the literal `true` turns
    webhooks on (`src/webhook/webhook-config.ts`). Unset, nothing is
    emitted or sent and every webhook route but the list answers `404`.
    The list returns `enabled: false`, so the Settings section renders
    the off state. Production does not set it, so webhooks stay off on
    wafflebase.io (see Carried over: decide whether to turn them on).
  - `WAFFLEBASE_SECRETS_ENCRYPTION_KEY` (#1191): 64 hex characters, which
    encrypts webhook signing secrets. Unset, it falls back to
    `DATASOURCE_ENCRYPTION_KEY`, which production sets. Only matters once
    webhooks are on. Changing the key in effect later makes existing
    secrets unreadable.
  - `WAFFLEBASE_WEBHOOK_ALLOWED_CIDRS`, `WAFFLEBASE_WEBHOOK_ALLOW_HTTP`
    (#1191): SSRF-guard overrides. Both fail closed.
  - `WAFFLEBASE_WEBHOOK_QUIET_MS` (60000), `WAFFLEBASE_WEBHOOK_MAX_WAIT_MS`
    (300000) (#1191): the `document.content_updated` coalescing window.
  - `WAFFLEBASE_DESKTOP_WINDOWS_ORIGIN` (#1195): only the literal `false`
    stops `POST /auth/desktop/session` accepting `http://tauri.localhost`
    (the Windows webview origin, which an ordinary browser can also reach).
    Unset keeps it accepted. **Recommend (ask first):** set it to `false`
    on wafflebase.io, since no Windows build ships in this release. Nobody
    needs the origin, and it is the weaker of the two desktop origins.
  - Unchanged from v0.6.18: `CHAT_LISTEN_DATABASE_URL` (#1191 moved the
    listener into a shared `common/pg-bus.ts` that the webhook worker uses
    too; it still falls back to `DATABASE_URL`, which reaches Postgres
    directly in production).
  - Frontend: `VITE_SERVICE_WORKER` (#1206), optional. The literal `off`
    unregisters the offline app-shell worker. Unset, the worker is
    registered only inside the desktop shell, and web visitors get none
    (`packages/frontend/src/lib/service-worker.ts`). `publish-ghpage` does
    not set it.
- [x] **New routes, frontend already ahead.** No route was removed or
      changed incompatibly, so a cached old frontend keeps working against
      the new backend. `browse` accepts the old category labels for one
      release (#1205). New routes:
      - `/workspaces/:wid/webhooks/*` and
        `/workspaces/:wid/members/:userId/removal-impact` (#1191)
      - `GET` / `DELETE .../chat/channels/:cid/members[/:userId]`
        (#1189, #1190)
      - `GET .../chat/channels/:cid/files` and
        `GET .../chat/documents/:documentId/channels` (#1201)
      - `POST /auth/desktop/session` and the `desktop` field on
        `GET /auth/providers` (#1195)

      The chat `clientId` falls back by itself: a frontend facing `v0.6.18`
      resends without the field (#1201).
- [x] **The image carries `@wafflebase/core` at runtime.** The backend now
      imports `@wafflebase/core/document-link` (#1201), and the `Dockerfile`
      copies `packages/core/dist`. CI's `verify-backend-image` boots the
      image.
- [x] **Desktop release prerequisites (#1206).** `desktop-release.yml` runs
      on `release: published`. Its signing jobs name the `desktop-release`
      Environment (required reviewers hackerwins / ggyuchive, `v*` tags
      only), which holds the Apple certificate, the App Store Connect API
      key and the minisign updater key. Its first job checks the tag against
      `packages/desktop/package.json` and `Cargo.toml`.
- [ ] **The desktop download links go live before the assets do.** Once
      the bump merges, the deployed frontend is `0.6.19`, so
      `offerDesktopDownload()` turns the homepage section on
      (`packages/frontend/src/app/home/desktop-download.ts`,
      `FIRST_DESKTOP_RELEASE`). But `releases/latest/download/…` answers
      `404` until the desktop run uploads the assets. Keep that gap short:
      publish the release right after the merge and approve the deployment
      at once.
