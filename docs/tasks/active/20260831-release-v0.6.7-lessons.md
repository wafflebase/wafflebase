# Release v0.6.7 — lessons

## An unticked box is not evidence of unfinished work, and ticking it is not free

Eight of the nine tasks archived in this pass had shipped weeks earlier
with their boxes never ticked. `tasks:archive` keys only on unchecked
boxes, so a merged PR alone never moves a task — the same finding v0.6.6
recorded, now confirmed as the steady state rather than a one-off.

(Counting trap worth naming: `tasks:archive` reports *files* moved, and
a task is one or two files depending on whether it has a `-lessons.md`.
"Moved 14 files" here was 9 todos + 5 lessons, not 7 pairs — and reading
it as 7 pairs is exactly the error this release's first commit message
shipped with, before the file list was actually counted. Count
`*-todo.md`, never the file total.)

The new part is the other direction. The obvious move is to sweep every
box in a shipped task's file to `[x]` and let the script do the rest.
That is wrong four times in this window alone:

| Task | Box | What the PR actually said |
| --- | --- | --- |
| `axis-order-selection-perf` | manual smoke at row 1,000,000 | #980: "**Not run**: browser smoke. No Postgres/Yorkie stack was up in this worktree and :8080 is answered by another checkout" |
| `shared-image-access` | incognito smoke on a shared deck | #955: "*(recommended before merge on a local `pnpm dev`.)*" — a recommendation, not a record |
| `sync-status-indicator` | re-smoke after Phase 6 | #967 records a smoke, but Phase 6 changed the toast and recovery paths afterwards |

A tick is a claim. Each of these would have asserted a session that
never happened, and the assertion would have outlived everyone who could
contradict it. They became plain bullets naming what was and was not run
— the convention v0.6.5 established for negative-form disclosures and
v0.6.6 reused for `docs-sync`, now applied to a second category:
**not-quite-done boxes on otherwise-shipped work**.

**Rule:** before ticking a box in a task you did not personally execute,
read the PR that shipped it. Tick what the PR evidences; convert the
rest to a bullet that says so. Archiving a task with three honest
bullets is worth more than archiving it with three false ticks.

## The same rule applies to the denial, and that is where it broke

A fourth box was demoted to a bullet reading "no record of it in #947."
That was **false**. #947 records the manual DevTools pass verbatim, in
its **"Notes for Reviewers"** section:

> Verified manually in Docs and Slides with DevTools filtered on
> fonts.googleapis.com — only visible rows request, more arrive on
> scroll, and keyboard navigation loads them too.

The cause was a search, not a judgement: the PR bodies were swept with
`grep -iA12 "test plan\|## Test"`, and #947 puts its manual verification
under a heading that pattern never matches. Finding no "Test plan"
section, the conclusion drawn was "no record" — an assertion about the
whole PR from a look at part of it. Two independent review agents caught
it, and it had already propagated into the archived task file, the
release todo, the lessons table and the commit message.

**Rule:** "no record of X" is a positive claim about the *whole*
document and needs the whole document read. A heading-scoped grep can
support "X is not in the test plan"; it cannot support "X did not
happen." When a PR looks like it is missing evidence, read its body end
to end before writing that down — and prefer wording that names where
you looked ("not in #947's test plan") over wording that claims
universal absence.

The asymmetry is worth stating plainly: an unsupported **tick** and an
unsupported **denial** are the same error wearing opposite signs, and
the caution that produces the first does nothing to prevent the second.
Being careful about not over-claiming made the under-claim feel safe.

## `- [ ]` appears in prose, and a blind sed will corrupt it

Ticking a whole file with `s/- \[ \]/- [x]/` mangled a line of
`notes-blockquote-lists-todo.md` that was *quoting markdown syntax*:

```
so `> - [ ] a` parses as a plain paragraph whose "content" is the whole line,
```

It became `> - [x] a`, which inverts the sentence's example. On a task
about checkbox parsing, the false positive is guaranteed rather than
unlucky — the file is *about* that string.

**Rule:** after any bulk box edit, read `git diff` filtered to the
changed box lines and confirm every one is a real checklist item. Anchor
the pattern at line start (`^\s*- \[ \]`), which is what
`grep -c` already used to count them, and which would have skipped this
line.

## `target-version` drifts behind reality, not just ahead of it

v0.6.6 found `debug-report.md` reading `0.7.0` for a feature that
completed in-window — a doc **ahead** of reality. This window found the
mirror image three times: `agentic-dev-loop.md`, `eval-harness-usage.md`
and `design-editor-packaging.md` all read `0.6.6`, but all three files
were **added after the v0.6.6 tag** and so ship in 0.6.7.

The cause is structural, not carelessness: a doc is written while
`package.json` reads the version currently in flight, and the release
cuts past it before the PR lands. Any PR merged between the release
branch cut and the next bump inherits a stale number.

**Rule:** audit `target-version` with `git log --diff-filter=A` on each
doc touched in the window, not by reading the number. The question is
"was this file added before or after the previous tag", and only the log
answers it.

## A fixes-only SDK bump still deserves the changelog read

`@yorkie-js/sdk` 0.7.17 → 0.7.18 has no API change, which makes it
tempting to bump and move on. Reading the four upstream PRs is what
turned it from "routine bump" into something the release notes can
justify: three of the four land on paths wafflebase exercises hard —
`RGATreeList.insert` anchoring (every slide/element/axis array), style
ranges collapsed by a merge at the `from` anchor (the docs inline-style
path), and the restore relink that undo rides.

**Rule:** for a dependency the product's correctness rests on, read the
release body and map each fix onto a path in this repo. If none map, say
so; that is also information.

## A pnpm minor mismatch DID churn the lockfile — by exactly one line

The repo pins `packageManager: pnpm@10.5.2`; the local binary is 9.15.9.
A first read of the diff called it "40 lines, every one a version
string." That was close but wrong, and a reviewer caught it: one
`vitest`/`vite` peer suffix had also flipped from `@types/node@22.14.1`
to `25.4.0`. Both resolutions already existed in the lockfile (147 vs 43
occurrences on `main`), so this was a single straggler being normalized
during relock — not a new dependency, but not the Yorkie bump either.

It was reverted, after first confirming that **both**
`vitest@4.1.8(@types/node@…)` snapshot keys exist in the lockfile — a
hand-edited reference pointing at a key that is not there is worse than
the churn.

**Rule:** filter the lockfile diff to the lines that are *not* the
intended change, and read what is left:

```
git diff main -- pnpm-lock.yaml | grep -E '^[+-]' | grep -v '^[+-][+-]' \
  | grep -v "<the version you meant to bump>\|integrity"
```

Zero lines out is the goal. "Every line looked like a version string" is
an impression; this command is a check. The integrity-hash lines are
expected — they belong to the bumped packages themselves — so exclude
them explicitly rather than eyeballing past them.

## Write both task files, then index — never between

`docs/tasks/README.md` shipped with `-` in the Lessons column for this
very task, because `pnpm tasks:archive` (which chains `tasks:index`) ran
*before* the lessons file was written. The index is a snapshot; running
it early records the tree as it was.

Two things make this easy to miss: `verify:fast` does **not** cover
`docs/tasks/README.md`, so the pre-commit gate is silent on it, and the
stale cell is a single dash in a table of 19 rows.

**Rule:** write `-todo.md` and `-lessons.md` first, archive second, and
if anything is written afterwards re-run `node ./scripts/tasks-index.mjs`
before committing. Cheap to re-run, invisible when skipped.
