# Release v0.6.13

**Created**: 2026-10-19

Cut `v0.6.13`. A routine release: no outage drives it. The backend has run
`v0.6.12` for a month while the frontend kept shipping from `main`, so the
main purpose is closing that gap. The largest backend change is the Yorkie
SDK at 0.7.25.

## Preconditions

- [x] **Production Yorkie is v0.7.25.** #1098 says to deploy the 0.7.25 SDK
      only against a 0.7.25 server (presence patches, yorkie-js-sdk#1477).
      `kubectl -n yorkie get deploy` reports `yorkieteam/yorkie:0.7.25`
      (checked 2026-10-19). The backend reaches it at
      `yorkie-gateway.yorkie.svc.cluster.local`.
- [x] **No backend change that needs a matching frontend.** `v0.6.12..main` touches
      `packages/backend` only through the three SDK bumps (#1089, #1096,
      #1098) and doc-path moves (#1082, #1095). It has no CORS, auth, or route
      change, so the v0.6.12 failure mode (a frontend ahead of the API it calls)
      cannot come from this window.

## Carried over from v0.6.12 (decision not taken)

Nothing enforces "the frontend may not be published ahead of the backend it
talks to". v0.6.12 listed the options (gate `publish-ghpage.yml` on the
backend's deployed tag, or keep the status quo and add a checklist question)
and asked for a choice at archive time. No choice was recorded. This window
contains no change that needs both halves (Preconditions above), so v0.6.13
does not force the decision. It stays open here rather than being marked
decided.

- [ ] Decide, and record the decision in `*-lessons.md`.

## Review

Deployed and verified on 2026-10-19. The backend caught up with a frontend
that had been a month ahead, and nothing broke, because no change in the
window needed both halves.

The one box not met as written is the pre-rollout image smoke. That gap is
structural rather than a one-off. Nothing stands between a non-booting image
and an outage except that smoke: `replicas: 1` and no readinessProbe. A
readinessProbe on `/health/ready` would let a bad image fail its rollout
while the old pod keeps serving. That belongs in devops, not this repo. See
the lessons file.

The task stays active for the carried-over frontend/backend skew decision
only.
