# Release v0.6.13 — lessons

## A shipped-but-unticked todo is the common case, not the exception

Four of the todos archived for this release had merged weeks earlier with no
box ticked: #1099, #1101, #1102, and the whole v0.6.12 rollout.
`tasks:archive` keys only on unchecked boxes, so they would have sat in
`active/` indefinitely.

**Rule:** at release prep, list every active todo's open boxes with the PR
numbers it cites, then check each box against `main` (or the live
deployment) before ticking it. Never tick from the merge alone. A box that
can only be ticked on indirect evidence says so in the file.

## The pre-rollout image smoke has no safety net behind it

The deployment runs `replicas: 1` with no readinessProbe. During a rolling
update the new pod counts as ready the moment its container starts, so an
image that crashes on boot replaces the working pod anyway. v0.6.10 went down
this way. The published-image smoke is therefore the only gate, and this
release could not run it:

- local Docker could not pull from Docker Hub at all (`hello-world` timed
  out; the CLI reached the daemon, the daemon reached nothing)
- auto mode refuses `kubectl run` in the production cluster as a
  shared-cluster mutation, so a one-off smoke pod was not an option either

What substituted was tree identity: the published image and #1103's
`verify-backend-image` smoke were built from the same tree (`1b8692f`).
That is strong evidence, not proof.

**Rule:** add a readinessProbe on `/health/ready` to
`k8s/wafflebase/deployment.yaml` in `yorkie-team/devops`. With one in place,
a non-booting image fails its own rollout while the old pod keeps serving,
and the smoke stops being the only thing between a bad tag and an outage.

## Who can do which deploy step

- Merging a devops PR does **not** deploy: the `wafflebase` ArgoCD app has an
  empty `syncPolicy`. Someone has to sync.
- From an agent session in auto mode, every cluster mutation is refused: a
  smoke pod, `kubectl set image`, and an ArgoCD `kubectl patch` sync.
  Read-only `kubectl get`/`logs` works, and that is enough for all of the
  verification.
- So the working split is that the agent prepares everything and verifies
  everything, and the human merges devops and presses Sync. A read-only
  watch on the deployment image let verification start the moment the sync
  landed.

## The browser and the backend use different Yorkie servers

The frontend connects to `api.yorkie.dev`. The backend uses the in-cluster
`yorkie-gateway`. An SDK bump that needs a matching server version (#1098)
therefore has **two** preconditions, and this release checked both: the
public server and the in-cluster `yorkieteam/yorkie:0.7.25`.
