# Lessons — release v0.6.6

## `mergeable: MERGEABLE` is not "ready to merge"

Deciding whether to hold the release for #954, the PR was reported to the
maintainer as "open and mergeable with no failing checks". Both halves were
true and the conclusion was still wrong: `mergeable` is GitHub's **conflict**
field, and the PR was `reviewDecision: REVIEW_REQUIRED`,
`mergeStateStatus: BLOCKED` — a 4,639-line change nobody had reviewed. The
maintainer chose "merge it first" on the strength of a readiness claim that had
not been checked.

Read `mergeStateStatus` and `reviewDecision` together, and never present a
merge option without them:

```bash
gh pr view <N> --json mergeable,mergeStateStatus,reviewDecision,additions
```

`mergeable` answers "would git apply this cleanly". `mergeStateStatus: CLEAN`
plus `reviewDecision: APPROVED` answers "may this land".

## Never let a pipe swallow a gate's exit code — again

v0.6.5 recorded this exact lesson, and it recurred here within the same
session: `pnpm verify:fast 2>&1 | tail -25` reported the notification
`exit code 0` while four frontend suites were failing, because the pipeline's
status is `tail`'s. The failure was only caught by reading the log body and
noticing `ERR_PNPM_RECURSIVE_RUN_FIRST_FAIL` in text that had been called
green.

A lesson written in a doc does not survive into the next session by itself.
The form that works:

```bash
pnpm verify:fast > /tmp/vf.log 2>&1; echo "EXIT=$?"; tail -12 /tmp/vf.log
```

This applies to every backgrounded gate, because the harness reports the
*pipeline's* exit code in its completion notification too.

## "CI is green, so it is my environment" is a hypothesis, not a conclusion

After the rebase, `frontend:test` failed locally with
`ERR_UNKNOWN_FILE_EXTENSION` for `debug-report/src/plugin/index.ts`. The
merge_group run on the identical commit had `frontend:test` passing in 136s, so
this was reported to the maintainer as a local environment problem, and a full
`rm -rf node_modules && pnpm install` was run on that basis. It reproduced
exactly.

The reasoning was backwards. "CI passes and I fail" narrows the cause to *some*
difference between the two machines — it does not establish that the difference
is broken state on mine. Here the difference was **Node**: CI's
`node-version: 22.x` resolved to v22.23.2, where type stripping is on by
default and Node can import a `.ts` file; local was v22.14.0, where it cannot.
Same tree, same lockfile, same install, different language support.

Name the difference before acting on it:

```bash
gh run view <id> --log --job <job-id> | grep -i "node: v"
```

One `grep` would have replaced a clean reinstall. And the reinstall's failure
was the useful result — it falsified the guess, which is why the guess should
have been tested before it was announced.

## A package added mid-window breaks local installs, not CI

The four failing suites could not resolve `@wafflebase/core/geometry` from
`debug-report/src/capture.ts`. Nothing was wrong with either package:
`packages/debug-report` arrived in this window (#946) and the local
`node_modules` had never been re-installed against it, so
`packages/debug-report/node_modules/@wafflebase` did not exist. CI installs
fresh every run and never sees this.

Generalizes v0.6.5's note about a stale Prisma client and an uninstalled
`@duckdb/node-api`: when a failure is a *resolution* or *compile* error rather
than a failed assertion, check `pnpm install` before reading any source.

## `tasks:archive` cannot see work, only boxes

Five of the seven tasks archived this window had shipped weeks earlier — #922,
#925, #926, #927, #786 were all merged PRs with every acceptance criterion
satisfied in the tree and not one box ticked. `tasks:archive` greps for
`- [ ]`; a merged PR is invisible to it. So the archive backlog is not a
measure of unfinished work, it is a measure of unticked boxes, and the only
way to tell them apart is to verify each task against the tree.

Six parallel agents (one per task group of four) did that for all 25 active
tasks in about four minutes of wall-clock. The conservative rule they were
given — "if you cannot find evidence it shipped, it is OPEN" — is what made
the output trustworthy: the two verdicts that came back KEEP-with-caveats were
more useful than the seven ARCHIVEs.

## Distinguish a task from a roadmap before trying to archive it

Four of the 18 tasks that stayed active cannot ever reach zero unchecked boxes
because they are not tasks: `docs-wordprocessor` (30 open items) is a
multi-quarter parity roadmap, and `slides-gradient-editing`,
`shared-core-extraction` and `design-editor-layout-sandbox` are multi-PR epics
where only PR 1 landed. Each sweep re-audits them and re-rejects them.

This is the same structural finding v0.6.5 made about negative-form
disclosures, one level up: a checkbox is pending work, a bullet is a
disclosure, and a roadmap belongs in `docs/design/`, not in
`docs/tasks/active/`. Splitting the shipped phase out so it can archive is
what stops the re-audit cost from recurring every release.

Related, and still unfixed: `tasks:archive` matches only `- [ ]`, so the six
`[~]` partial-progress boxes in `docs-wordprocessor` are invisible to it. A
file left with nothing but `[~]` items would auto-archive with real work
outstanding.
