# Release v0.6.12

**Created**: 2026-09-18

Cut `v0.6.12`. This is an **outage release**: production login has been broken
since this morning, and the fix is already on `main` — it just is not in a
tagged image.

## Why this release exists

`wafflebase.io` could not sign anybody in. Clicking **Continue with GitHub**
ran the whole OAuth round trip and returned the browser to the landing page,
still logged out, with no error message.

The cause is a **frontend/backend version skew that this repository's two
deploy paths produce on their own**:

- `publish-ghpage.yml` publishes the frontend to `wafflebase.io` (GitHub Pages)
  on **every green CI run on `main`**.
- The backend on EKS (`api.wafflebase.io`) is pinned to a **release tag** —
  it was running `yorkieteam/wafflebase:v0.6.11`.

So when [#1076](https://github.com/wafflebase/wafflebase/pull/1076) (Sentry)
merged at 07:28 KST today, the frontend carrying it went live at ~08:55 KST
while the backend stayed four days behind.

That frontend attaches `sentry-trace` and `baggage` to every request bound for
its own API origin (`tracePropagationTargets: [origin]`,
`packages/frontend/src/sentry.ts`). #1076 added both to the backend's CORS
allow-list for exactly that reason, and said what happens without it:

> a preflight that refuses them does not merely lose the trace — it fails the
> request.

v0.6.11's `main.ts` allow-lists only `Content-Type, Authorization`. So **every
credentialed browser call to the API was blocked by the preflight** — including
`/auth/me`. The OAuth callback really did set the session cookies; the app then
had no way to read the session back, so it rendered logged-out. Login was
impossible for anyone not already holding a working session.

Measured against the live deployment before the fix:

```
$ curl -X OPTIONS https://api.wafflebase.io/auth/me \
    -H 'Origin: https://wafflebase.io' \
    -H 'Access-Control-Request-Method: GET' \
    -H 'Access-Control-Request-Headers: sentry-trace,baggage'
HTTP/2 204
access-control-allow-headers: Content-Type,Authorization      # <- refuses both
```

Not the cause, recorded so it is not re-investigated:

- `GET /auth/providers` answers **404** on v0.6.11 (it arrives with
  [#1068](https://github.com/wafflebase/wafflebase/pull/1068)).
  `fetchAuthProviders()` degrades to "GitHub only" and never throws, so the
  login page renders correctly. It is a symptom of the same skew, not the
  break.
- Two `GET /auth/github/callback -> 400` in the backend log from **2026-09-14**
  are older and unrelated to this outage: that status is the CLI-state branch
  of the callback (`CLI login state expired, invalid, or completed in a
  different browser`), not the web branch. Today's failure logs nothing at all
  — the browser blocks the call before it is sent.

## The lesson this outage is evidence for

Nothing enforces "the frontend may not be published ahead of the backend it
talks to". The two paths are independent by design — Pages on every merge, the
API on a release tag — so **any** change that needs both halves breaks
production between the merge and the next release. #1076 is simply the first
one to hit a request the app cannot function without.

Worth a follow-up, not decided here:

- Pin the backend deployment to `latest` and let it move with `main`, matching
  the frontend's cadence; or
- gate `publish-ghpage.yml` on the backend's deployed tag; or
- keep both and treat "does this change need the other half?" as a release-note
  question, which is the status quo plus a checklist item.

Capture the choice in `20260918-release-v0.6.12-lessons.md` at archive time.
