# Lessons — Release v0.6.9

## The release checklist's own last section is the one that rots

v0.6.8's seven post-merge boxes sat unticked for three days. The release
had gone perfectly — annotated tag on the merge commit, GitHub Release
marked Latest, npm `dist-tags.latest` moved, a genuine multi-arch OCI
index, devops#349 moving all six lines, and a pod that had been running
`v0.6.8` with zero restarts since twelve minutes after publication.
Every fact was true on the day and every one still verified three days
later. Nobody wrote any of it down.

The cost is not that the release was wrong. It is that the task stayed
in `docs/tasks/active/` through the whole v0.6.9 window and arrived at
this release's archive audit **as an open task**, indistinguishable from
unshipped work, forcing a full re-verification pass — registry, Docker
manifest, the devops commit's patch, `kubectl get pod` — to re-establish
what was known at the time.

The structural reason is worth naming, because "remember to tick the
boxes" has now failed at least three releases running. A release
checklist is written *before* the release and its last section is read
*after* it, at the point where the work feels finished and the branch is
already merged. There is no artifact left to attach the tick to: the PR
closed days earlier, and the remaining steps happen in a registry, a
different repository, and a cluster.

**Rule: the post-merge section closes in the same sitting as the rollout
check.** The pod verification is the last step that produces evidence, so
it is the natural place to write the evidence down. If you are running
`kubectl get pod` you are already in the sitting where the section
closes.

And the sharper version, because this failure is recursive: v0.6.8's own
archive audit is ninety lines about tasks that shipped with their boxes
never ticked — it even contains the phrase *"the exact 'shipped with the
boxes never ticked' state v0.6.7 archived nine tasks out of"* — and then
did precisely that to itself, in the section immediately below. **An
audit that only ever runs over other people's tasks will keep finding
this.** Run it over your own first.

## An absence in a filtered list is not an absence

This release drafted a confident correction to the release checklist —
that v0.6.8's "`npm-publish` and `docker-publish` green" box was
**unsatisfiable**, because `docker-publish.yml` fires only on pushes to
`main` and therefore never produces a version-named run. It reached the
release notes, the archived v0.6.8 doc *and* this lessons file as a
generalizable rule before the branch's own claim audit refuted it.

`docker-publish.yml` has two triggers and has since #803, which landed
before v0.6.7. It waits on CI for `:latest` and keeps a direct
`release: types: [published]` trigger for tagged images. There is a green
run titled `v0.6.8`, and one for every release back to v0.4.6.

**The mechanism is worth more than the correction.** The evidence was a
single command:

```bash
gh run list --workflow=docker-publish.yml --limit 5
```

Five rows came back, all titled "Docker Publish", none version-named —
because the `workflow_run` runs that publish `:latest` are an order of
magnitude more frequent and fill the first page. From *no version-named
run in this page* the draft concluded *no version-named run exists*, and
then escalated that into a claim about the trigger configuration,
**without ever opening the workflow file** — whose first eight lines are
a comment explaining both triggers and why the second one exists.

Three rules, in increasing order of how much they would have saved:

1. **A `--limit`ed, unfiltered list is a sample, not a census.** If the
   claim is "none exists", the query must be able to see all of them:
   `--event=release`, or a limit past the frequent case.
2. **A claim about configuration is answered by the configuration.** The
   question was "what triggers this workflow", and the workflow file
   answers it in one `Read`. Inferring a trigger from run history is
   indirect evidence for something available directly.
3. **A negative claim needs stronger evidence than a positive one**, and
   this one was load-bearing: it told the next releaser to *skip* a
   check. A wrong correction to a checklist is worse than no correction,
   because it removes a working gate and carries the authority of having
   been "audited".

The near-miss is the point. Every other claim in this release was
re-derived from source; this one was derived from a convenient listing
and then reused three times, gaining apparent solidity from repetition
rather than from evidence. **Repetition across documents is not
corroboration** — all three copies had one source.

## Ten open boxes describing work nobody intends to do

The template-gallery pair carries ten boxes for frozen-copy promotion — a
system workspace, approval copying into it and re-pointing `documentId`,
republish-supersedes-and-deletes, promotion-time image re-hosting. Both
files' Review sections record that promotion was **deferred in favour of
re-review-on-change**. So the boxes describe a design that was
consciously replaced, and they will read as pending work at every future
audit until somebody strikes them.

This audit did **not** tick them — ticking a box claims the work shipped,
and it did not. **Four of the ten** were annotated `**dropped**` in
place, with the surviving fragments named honestly: the generic
`rehostImages` walker did ship, but on the copy engine rather than on a
promotion path that does not exist, and `originId` survives as a schema
column with no writer. The other six, in
`template-gallery-public-tier`, got nothing — that file was never opened
by this branch. The half-done state is itself the lesson: the annotation
pass stopped at the first file and the summary generalized to both, which
the claim audit caught.

`scripts/tasks-archive.mjs` keys on `- [ ]` and nothing else, so a
cancelled box, a recorded non-goal and genuine unshipped work are all the
same character to it. `20260729-design-editor-layout-sandbox` has seven
such boxes — six CP4.4 sub-boxes the file itself marks *"Cancelled by
design decision, not outstanding"*, plus a non-goal written as a
checkbox.

**Rule: when scope is dropped, strike the boxes in the same change that
records the deferral.** A Review section saying "deferred" and a
checklist still saying `- [ ]` disagree, and the checklist is what the
tooling reads. Three options, in order of preference: delete the boxes,
convert them to prose under a "Dropped" heading, or — if they must stay
as spec — move them out of the checklist entirely.

## Re-verify, do not inherit, a previous audit's spot-checks

v0.6.8's audit recorded five source spot-checks. Its own notes already
caught one expiring mid-flight: `packages/core/src/` held exactly three
subpaths when checked, and `image/` was added forty minutes later.

This audit re-derived all of them rather than carrying them forward, and
that was the right call twice over. Two findings **inverted**:

- `revision-history`'s upstream `preprocessYSON` box still read *"Latest
  SDK is 0.7.18, so there is no version to bump to."* The fix shipped in
  `@yorkie-js/sdk@0.7.19` and #1017 bumped it.
- The same file's PR-3 box read *"Not started — still blocked on the
  upstream `YSON.parse` tokenizer."* #1017 shipped it.

Both boxes described a world that ended when one PR merged. Neither
would have been caught by re-reading the task doc, only by checking the
tree.

And one prior finding **stopped being safe to act on**:
`template-gallery-public-tier` says *"Remove `DELETE /images/:id` …
Confirm no client calls it."* There is now a client —
`wafflebase images delete` (`packages/cli/src/commands/images.ts:186`) —
shipped by #999 after the box was written. Executing that box as written
would break a released CLI command.

**A spot-check is evidence with a timestamp.** Quote the date you took
it, and re-take it rather than citing it.

## The one task that was 16-unchecked-and-fully-shipped

`20260903-api-v1-folders-copy` sat at 16 unchecked / 0 checked while
every line of it was on `main` — #1012, two days old. Not one box was
partially done; the whole task had landed.

This is the clearest instance yet of the pattern, and it points at the
mechanism rather than at forgetfulness: **the PR is the unit of
attention and the task doc is not part of the PR's own checklist.** The
author finishes the branch, the reviewer reviews the branch, CI gates
the branch, the merge queue merges the branch. The task doc lives in the
same repository and is touched by none of those steps.

Worth considering as a durable fix rather than another resolution: a
`verify:fast` check that a task doc modified in a PR has no unchecked
box whose work the same PR ships is not expressible, but a
**pre-merge prompt** — "does this PR close boxes in
`docs/tasks/active/`?" — is, and it belongs in the PR template where the
attention already is.

## Six parallel audits, one shared instruction that did the work

The archive audit ran as six concurrent investigations over 29 tasks.
The instruction that mattered was not the split; it was:

> Verify SHIPPED verdicts by finding the actual code — quote the file
> path and the specific symbol. Do NOT trust a commit message.

Every audit came back with `file:line` evidence, and several came back
with verdicts *contradicting* what the commit messages implied — the
BigQuery dry-run box is not satisfied by the one `dryRun: true` in the
service (that is a private `probe()` running `SELECT 1` to validate IAM,
and `totalBytesProcessed` appears nowhere), and lakehouse's `_delta_log`
handling is the **opposite** of the path detection its box asks for: it
rejects a path pointing at `_delta_log`.

Both would have read as shipped to anyone grepping for the identifier
and stopping there. Grep finds the string; only reading the function
finds the verdict.

## Manual browser smokes are the residue, and they are not an agent's to close

Three tasks — `board-nested-doc-update`,
`yorkie-0719-docs-revision-preview`, `dependabot-28-alerts` — have
exactly one open box each, and in all three it is a click-through in
`pnpm dev`. All the code shipped and is verified by tests.

They were deliberately left open. The `yorkie-0719` task records the
reason in its own Review: the app has no session and signing in goes
through GitHub OAuth, which an agent must not perform. So this is not a
gap in the audit — it is the correct boundary, and the honest report is
"three tasks are one human browser session away from archivable", not
three more archived tasks.

Worth noting for planning: the manual-smoke box is now the single most
common reason an otherwise-finished task cannot archive. Batching them —
one browser session closing three tasks — is cheaper than three
separately, and it is the highest-yield hour available to a human before
the next release.

## `tasks:archive` does not fix inbound links to what it moves

Archiving `20260903-api-v1-folders-copy` broke a link:
`20260831-agentic-office-workflow-todo.md` referenced it as
`./20260903-api-v1-folders-copy-todo.md`, which stopped resolving the
moment the file moved to `docs/tasks/archive/2026/09/`.

`scripts/tasks-archive.mjs` renames files and rebuilds the two index
READMEs. It does not rewrite references *into* the moved files, and
nothing about the move announces that it should. `pnpm verify:doc-links`
caught it — one dead link, named precisely — but only because that check
runs in `verify:fast`; the archive step itself reported success.

**Rule: after `pnpm tasks:archive`, run `pnpm verify:doc-links` before
anything else.** Cheaper still, grep first for what is about to move:

```bash
grep -rl "$SLUG" docs/tasks/active/ docs/design/
```

This will recur every time an archived task is one another task cites as
its predecessor or successor — which is exactly the tasks most likely to
be archived, since finished work is what gets referenced as done.

## Every false claim this release made was a true claim, upgraded

The claim audit killed eleven statements. Not one was invented, and not
one was careless about a fact nobody had checked. Every single one had a
true claim underneath it that had been strengthened into a better
sentence:

| true | shipped in the draft |
| --- | --- |
| `=64` yields 2 when 32 was available | "2 — *lower* than leaving it unset" |
| SP2–SP4 shipped in v0.6.3 | "across three later versions" |
| 4 boxes annotated `dropped` | "they were annotated in place" (of 10) |
| 276 turns for the code-fix agent | "276 turns" as the run total |
| 3 open follow-ups | "nine … three of them in that same class" |
| 12 source files, 11 tests | "11 source files against 11 test files" |
| 2 pages named those menu items | "four told readers to click…" |

The direction is always the same: toward the sentence with more rhetorical
force. "Lower than unset" is a better bug than "equal to unset". "Three
later versions" makes the convention argument harder than "one". A single
turn count reads cleaner than "276 for one agent and 1456 for another".

This is not lying and it does not feel like lying while it happens — each
one is a rounding, a merge, or a generalization applied to real evidence
that was gathered honestly minutes earlier. Which is exactly why it
survives a re-read: re-reading checks whether the sentence is *supported*,
and every one of these is nearly supported by the note it came from.

**The countermeasure is the instruction, not the effort.** The audit that
caught all eleven was told to *falsify*, not to *review*:

> Re-derive it independently and report whether it HOLDS or FAILS.
> Prioritize every number, every superlative, every claim with a file
> path.

A reviewer asked to check the release notes would have read them and
found them plausible — they are plausible, that is the failure mode. A
reviewer asked to break each sentence runs `git tag --contains`, opens
the workflow file, and counts the directory. The eleven failures are all
one command deep. **None of them required judgment; all of them required
somebody to actually run the command instead of recalling the answer.**

Concretely, for the next release: the claim audit is not optional and it
is not the same activity as the self-review. Give it the falsify framing
verbatim, give it the file list, and require it to report what HELD as
well as what failed — an audit that reports only failures cannot be
distinguished from one that stopped early.

## A wrong correction is worse than no correction

The `docker-publish` error deserves separating from the other ten,
because it was not an upgrade of a true claim — it was a false claim that
had been promoted to a *rule*.

It appeared in three documents and became a lessons-file heading ("A box
can be unsatisfiable and still get ticked"), complete with a
generalization: *"A checklist item that has never once been checked
against its own literal wording is not a checklist item; it is a
sentence."* That generalization is good advice attached to an example
that is false. And its practical output was a v0.6.9 checklist box
reading "`npm-publish` green. **Not** `docker-publish`" — instructing
every future releaser to skip a check that works and has worked since
v0.4.6.

Two things went wrong in sequence, and only the second is unusual:

1. An absence in an unfiltered, `--limit`ed list was read as an absence
   in the world (see the previous lesson).
2. That reading was then **generalized into a rule about the system**
   rather than kept as an observation, and the rule was written into the
   place future releases take instructions from — without the
   thirty-second check (`Read .github/workflows/docker-publish.yml`) that
   the promotion to a rule should itself have triggered.

**Rule: the bar for a claim rises with where you are about to write it.**
An observation in a Review section costs a re-read if wrong. A rule in a
lessons file, or a box in a checklist, is executed by people who will not
re-derive it — so a claim being promoted to either needs its evidence
re-gathered *at the moment of promotion*, from the most direct source
available. If the claim is about how a workflow triggers, that source is
the workflow file, not its run history.

The retraction was kept in place in all three documents rather than
silently deleted, for the same reason: the next person to notice that
`docker-publish` has no version-named runs on its first page should find
the answer already written down.

## A clean rebase does not protect you from the merge queue

v0.6.8 learned that a PR landing mid-flight invalidates a release's
counts, and wrote it down: *"a clean rebase is not the same as a
still-true document."* This release followed that checklist, rebased,
found `main` unmoved, verified the window was still 17 commits — and then
**#1027 merged nineteen minutes ahead of #1028 while both sat in the
merge queue.**

So the tag covers 18 commits and the draft described 17. Every count in
the release notes was off by one PR, and one substantive fix had no
highlight at all.

The distinction from v0.6.8's version matters, because the fix is
different. There, the other PR had *already landed* when the rebase ran,
so the rebase could surface it and did. Here the rebase was genuinely
clean and the other PR landed afterwards. **No step in the pre-push
sequence could have caught this**, and adding more diligence to the
rebase would not have helped.

**Rule: recount the window after the merge and before the tag.** The tag
is the first moment the window is final, and it is the last moment before
the numbers become public in the release notes. One command:

```bash
git log --oneline v<prev>..<merge-commit>^ | wc -l
git diff --shortstat v<prev>..<merge-commit>^
git log v<prev>..<merge-commit>^ --format='%an' | sort | uniq -c
```

Anything that moved gets fixed in the GitHub Release body — which is
authored at that moment anyway, so the cost is zero — and then in the
task doc. That is what happened here: the release notes cover #1027, the
task doc carries the corrected 18 / 361 files / +37,816 and a
`@hackerwins 16`, and the discrepancy is written down rather than
silently reconciled.

A merge queue makes this **structural, not occasional**: the whole point
of the queue is that other PRs merge between your last push and your
merge. Any release process that computes its numbers before entering the
queue will be wrong exactly as often as somebody else is merging.

## "The workflow is green" is not "the artifact is published"

`npm-publish` reported `success`. The registry, queried directly at that
moment, had no `0.6.9` and still pointed `latest` at `0.6.8`.

It resolved benignly — the publish had genuinely succeeded
(`+ @wafflebase/cli@0.6.9`) and npm's own notice says the package "may
take a few minutes to become available", so it was propagation lag. But
**the green check could not distinguish that from a failed publish**, and
neither could I until I read the run log. A release closed on the
workflow status alone would have recorded a published package on the
strength of a success no consumer could yet act on.

This is the box that says *confirm from the registries, not from the
workflow logs* doing exactly the work it was written for — and it needed
one refinement to actually do it:

**Rule: poll the registry, do not sample it once.** A single check
immediately after a green workflow tests propagation speed, not
publication. Loop until `dist-tags.latest` is the version you shipped:

```bash
until curl -s https://registry.npmjs.org/@wafflebase/cli \
  | python3 -c "import sys,json;sys.exit(0 if json.load(sys.stdin)['dist-tags']['latest']=='0.6.9' else 1)"
do sleep 20; done
```

Query `registry.npmjs.org` rather than `npm view`, which reads through a
cache and can report a stale answer long after the registry is correct —
the failure mode where the *check* is wrong instead of the artifact.

Docker needed no wait at all: the manifest was a complete multi-arch
index the moment the workflow finished. The asymmetry is worth knowing,
because it means "one of the two registries lagged" is the normal case
rather than a signal that something broke.

## Count a version bump; do not read it

The devops manifest carries the wafflebase version on **six** lines: two
`image:` references and four `app.kubernetes.io/version` / `version`
labels. devops#343 and #344 both moved some and missed others, and
devops#346 existed only to clean that up — which is why the checklist
says "bump **all six lines**" in bold.

It nearly happened again here. The first pass used:

```bash
sed -i '' 's/^\(\s*\)version: 0\.6\.8/\1version: 0.6.9/g' deployment.yaml
```

BSD `sed` on macOS does not support `\s`. The expression matched nothing,
**exited 0, and printed no warning** — so four of six lines moved and the
two bare `version:` labels stayed at `0.6.8`. A skim of the diff would
have shown four plausible-looking changes and no error.

What caught it was not care, it was arithmetic: counting the remaining
occurrences instead of looking at the ones that changed.

```bash
grep -c '0\.6\.8' deployment.yaml   # must be 0
grep -c '0\.6\.9' deployment.yaml   # must be 6
```

**Rule: a mechanical edit is verified by counting what should be gone,
not by reading what changed.** A find-and-replace that silently matches
nothing is indistinguishable from one that worked, unless you ask how
many are left. Generalizes past this file: the same shape catches a
partial rename, a half-applied codemod, and a version bump that missed a
manifest.

(Portability note for anyone scripting this on macOS: use `perl -pi -e`,
which takes the same expressions on both platforms, rather than
discovering per-flag `sed` differences one silent no-op at a time.)
