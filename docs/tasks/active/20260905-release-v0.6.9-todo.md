# Release v0.6.9

Close out v0.6.9 over the `v0.6.8..HEAD` window. Theme: **a document stops having only one
state — every CRDT type gets version history, a PDF's text becomes
readable by the person and not just the renderer, the template gallery
opens to the public with something in it, and a four-part audit stops
the documentation describing a product two releases old**.

**Window: 18 commits, 3 authors, 361 files, +37,816 / −1,926**
(`v0.6.8..8b7b16d8c`, the tip before the release commit).

**These are not the numbers this document was drafted with, and the
difference is the point.** It was written against a 17-commit window
(315 files, +33,970 / −1,805) and rebased cleanly onto an unmoved `main`
minutes before pushing — and then **#1027 landed while #1028 sat in the
merge queue**, nineteen minutes ahead of it. Its highlight is below,
added after the tag; every other count in this document was recomputed
against the real window rather than adjusted by one.

v0.6.8's release doc recorded exactly this ("a clean rebase is not the
same as a still-true document") after #1005 landed mid-flight, and this
release repeated it despite the warning being in the checklist it was
following. The difference is *when*: v0.6.8 caught it at the rebase,
before writing the notes. Here the rebase was clean and the PR landed
afterwards, so nothing in the pre-push sequence could have caught it. The
only step that can is a **post-merge recount before tagging**, which is
now what produced these figures — and it is why the GitHub Release notes
cover #1027 even though the draft did not.

**Patch (not minor) bump.** No new document type — `Document.type` still
routes the same eight — and no new workspace package:
`git diff --name-status v0.6.8..HEAD | grep '^A' | grep package.json`
returns nothing. The window's three largest items are a feature built
entirely on an SDK capability that was already pinned (#1010), a third
phase of an existing sidecar-table feature (#1009, #1026), and an
`/api/v1` surface over endpoints that already shipped (#1012). The
standing convention reserves a minor for a new document type. Patch,
consistent with v0.6.5 through v0.6.8.

## Yorkie SDK moved this release, and for a nameable reason

`@yorkie-js/sdk` and `@yorkie-js/react` go **0.7.18 → 0.7.19** (#1017),
pinned exactly across frontend, backend and notes. Unlike a routine
refresh this bump has a defect behind it. Through 0.7.18 `YSON.parse`
preprocessed a snapshot with a chain of regexes that bottomed out at

single-pass string-aware scanner — the upstream ask
`docs/design/revision-history.md` §6 recorded as
[yorkie-team/yorkie#1966](https://github.com/yorkie-team/yorkie/issues/1966).

No server-image pin moved: `docker-compose.yaml` and `ci.yml` both track
`yorkieteam/yorkie:latest`.

**Three Prisma migrations land** (all from #1009):
`20260902090000_add_template_listing_review`,
`20260903090000_add_template_listing_content_watermarks`,

## Highlights

### Product — Version history

**Every CRDT document type gets version history** (#1010, #1017). Through
v0.6.8 a document had exactly one state: the current one. There was no
way to see yesterday's version, mark a milestone, or get back from a bad
edit once the per-session undo stack was gone.

The whole feature is built on material Yorkie already stored.
`createRevision` / `listRevisions` / `getRevision` / `restoreRevision`
plus `@yorkie-js/react`'s `useRevisions()` were already pinned, and
Yorkie writes an automatic revision on every server snapshot — so this
adds **no persistence and no backend endpoint**. The only backend
production file its *authorization* touches is
`yorkie-auth.controller.ts`; the docs-preview half additionally rewrites
`src/yorkie/docs-tree.ts`, which is the extraction described below. What
ships is a shared frontend module (`components/history/`, 12 source files
alongside 11 tests and 5 YSON fixtures captured from a live server)
owning the day-grouped panel, the metadata contract, and a per-type
read-only preview hydrated into each engine's existing in-memory store.

Because the revisions are snapshot-shaped, the timeline is
**activity-shaped, not clock-shaped**, and automatic revisions carry no
author — so they render a time rather than a guess at who.

Authorization needed exactly one change, and it is the interesting one.
`ListRevisions` and `GetRevision` arrive with verb `r`, which a
share-link **viewer** passes — but `getRevision` returns a full snapshot
of every past state, including content deleted before the link was
shared. `REVISION_READ_METHODS` requires the same editor-or-member
authority a write does for those two, leaving every other method
untouched. A viewer can still read the document; they lose its history.
Restore is made non-destructive by writing a "Before restore" safety
revision first, and a failure to create it **aborts** the restore.

**This carries a deployment step, not a flag.** Merging exposes the panel
the moment the frontend deploys. Register `ListRevisions`, `GetRevision`
and `RestoreRevision` on the Yorkie auth webhook *and* set
`YORKIE_AUTH_WEBHOOK_ENFORCE=true` — shadow mode allows every request
regardless of the decision it computes, so registering alone protects
nothing. Do **not** register `CreateRevision`: Yorkie calls the webhook
for it with `attributes: null` for every caller, so `decide()` fails
closed and denies it to everyone, the owner included.
`packages/backend/README.md` carries the exact `yorkie project update`
invocation.

Docs was the one type with no preview at merge, and it shipped four days
later once 0.7.19 unblocked it. Getting it right required moving the
CRDT tree read walk out of the backend — it lived only in a NestJS-bound
module a browser cannot import, and copying it would have given the two
readers independent opinions about a format they must agree on. It now
lives in `@wafflebase/docs`'s `model/crdt-tree.ts`, reading a structural
node rather than the SDK's `ElementNode`, which is what keeps that
package free of any `@yorkie-js` dependency.

The failure that seam guards against is not a crash. A parsed snapshot
node and a live Yorkie proxy node disagree twice — the attribute key is
`attrs`, not `attributes`, and values stay JSON-encoded
(`"align": "\"center\""`) — and **neither disagreement throws**. Left
unhandled, every block falls back to `paragraph` with no style and no
table, rendering plausible content that is not what the user wrote.

### Product — PDF

**Select, copy, and comment on text in a PDF** (#1015, @ggyuchive). A PDF
page was only a canvas: text could not be selected, copied, or found with
the browser's own Ctrl/Cmd-F, and commenting meant drawing a box around
words the viewer could not read.

The fix **adds no dependency** — pdf.js's own `TextLayer` ships inside
the `pdfjs-dist` already installed, and this overlays it. Spans are
positioned as percentages of the unscaled `rawDims` viewBox, so the layer
renders once per page and a resize rewrites one CSS variable instead of
re-laying it out. Sizing is hand-rolled rather than pdf.js's
`setLayerDimensions`, which emits a `round()` against a
`--scale-round-x` only the full pdf.js viewer defines — invalid here, and
silently dropped. pdf.js now loads once in `PdfViewer` instead of once
per page, and a text-layer failure leaves the page readable.

Selected text becomes the primary comment anchor, and the anchor stores
**geometry, not text offsets**: PDF bytes are immutable, so there is
nothing for an offset anchor to survive. Typeset runs are joined back
into line bands bounded by a gap threshold, which is what keeps a
two-column page as two highlights rather than one drawn across the
gutter. The region tool stays, relabelled, for scans, figures and table
whitespace.

A scanned page yields no spans. That is OCR's job, designed in the new
`docs/design/ocr.md` and explicitly **not built here** — the doc
separates the two problems that get conflated (a PDF that *has* a text
layer needs no OCR; a scan does) and names the two real costs: this
backend has no job queue, and model binaries would have to be baked into
the image the way the lakehouse bakes DuckDB extensions.

### Product — Templates

**The public tier opens, and the gallery has something in it** (#1009,
#1026). Reading a template from outside its workspace was never the
missing piece — `unlisted` has done that since Phase 1. What the public
tier adds is discovery and trust: browse and search, review before
listing, a takedown that works, and a defence against a listing meaning
one thing when it was approved and another afterwards.

`visibility` is the effective tier and `status` is the review state, and
keeping them apart is what makes submitting observably a no-op: an
unlisted link already handed out keeps resolving, and a workspace listing
does not silently widen while a reviewer looks at it. `public` has
exactly one writer, the approve arm of `POST /templates/:id/review`;
publish and update refuse the *transition* into it rather than its
presence, because both fall back to the stored visibility and a check on
the value alone would leave an approved listing permanently
unpublishable. A **rejection** says the submission missed the bar and
leaves the listing working at the tier it had; a **takedown** says the
content may not be served at all, so it refuses every non-manager read,
revokes the preview link, and is terminal — including against
`unpublish`, because deleting the row would make the next publish a
`create` that mints a fresh anonymous link to the content that was
removed.

A public listing points at a live document, so a publisher could get one
thing approved and edit it into another. Content edits never reach this
backend except as Yorkie's `DocumentRootChanged` webhook, and an edit to
an approved listing now returns it to `pending`. But a status is only as
good as the write that set it, and that write comes from a webhook a
deployment registers per project — so the listing carries a content
watermark the read path re-checks, which stays correct when nothing ran.
Approving is an attestation: the queue hands the reviewer the watermark,
the approval echoes it, a mismatch is a `409`.

Building it turned up **two defects in already-shipped code**.
In-document images upload workspace-scoped and read back through an
access-gated route, so a template used in a *different* workspace has
arrived with every image 403ing since Phase 1 — hidden because the
preview carries a share token and renders fine while the copy the user
receives does not. Re-hosting now runs inside `DocumentCopyService` on
any cross-workspace copy, so it repairs `use` rather than decorating the
gallery. And `DELETE /images/:id` was guarded by `JwtAuthGuard` and
nothing else, with no client — harmless while ids stayed inside a
workspace, a vandalism path the moment a gallery publishes them.

Then the gallery was empty, and the pages leading to it read as a
different product: `/` is a bespoke marketing skin while `/templates` and
`/t/:id` were plain in-app chrome with no nav and no footer, so following
the Templates link looked like leaving the site. Both public routes now
mount a shared `MarketingPage`; `TemplateGallery` gains a `skin` seam
whose `"app"` default is what the test pins, because that default is the
property whose loss would leak marketing chrome into the workspace
Templates tab and it is invisible in review.

Two operator commands fill a deployment's gallery. `seed:templates`
creates ten documents from a catalogue authored in-repo as TypeScript —
so it typechecks against the real document models and reuses
`BUILT_IN_LAYOUTS` / `DEFAULT_MASTER` instead of duplicating a theme
catalogue into a fixture — and everything in it is written for this
repository and Apache-2.0 licensed, which is a constraint rather than a
note: Canva, Slidesgo, Google Slides and Office galleries are free to
*use* and not free to *redistribute*. `register:templates` then drives
publish, submit and approve through the product's own Share dialog with
Playwright. **That ordering is forced, not stylistic**: a template's
picture is captured by whichever editor is mounted at publish time, and
`thumbnailId` is a `CARD_FIELD`, so attaching it after approval returns
the listing to review and attaching it while `pending` is refused —
leaving exactly one window. The seed therefore keeps **no**
service-level publish path, since a second door would be the unguarded
way to swap an approved gallery card that `publish()` exists to prevent.

Reproducing that flow surfaced that the Share dialog could not set a
description at all: the column, the DTO, the frontend type, the gallery
card and `/t/:id` all carried one and no control ever sent it, so every
listing published through the product had `description: null`.

Two limitations are documented rather than papered over: registering is
not idempotent and cannot be, and `seed:templates` writes with a
tokenless Yorkie client while `register:templates` requires the auth
webhook **enforced** — so documents must be seeded *before* those
methods are registered on the project.

### API / CLI

**Folders, copy and move-to-folder become reachable without a browser**
(#1012, @yorkie-agent[bot]). Seven capabilities the web editor uses daily
had a backend but only behind `JwtAuthGuard` on a bare `@Controller()`.
`jwt.strategy.ts` also reads a Bearer header, so a `wafflebase login`
session reached them; an API key could not, because `/api/v1` is the only
surface `CombinedAuthGuard` is mounted on.

The close is a new `/api/v1` surface rather than a wider guard, for a
security reason rather than a stylistic one. `WorkspaceScopeGuard` is
what refuses a key minted for another workspace, and it works by reading
`:workspaceId` out of the path; the web routes are `folders/:id` with no
workspace in the path at all, so swapping `CombinedAuthGuard` onto them —
the smaller diff — would have left nothing for it to check and let any
valid key rename or delete any workspace's folder.

Exposing folders to keys then forced the authority model to be made
real, and this is the consequential half. Waving every API-key caller
past the manager bar rested on `WorkspaceScopeGuard` alone, which
compared the key's frozen `workspaceId` claim to the route param and
never consulted `WorkspaceMember` — so **removing somebody from a
workspace left every key they had ever minted working with full authority
over it**, destructive folder deletes included. A key now carries the
authority of the user who minted it, resolved at request time; the image
read route, the one v1 controller that cannot mount the guard because it
also serves anonymous share-token viewers, repeats the membership check
by hand; and `removeMember` revokes minted keys in the same transaction
as the membership delete. Copy is the deliberate exception, gated on
membership alone, because it neither modifies, moves, nor destroys the
source.

On the CLI: a `folders` namespace plus `docs copy` and `docs move`, each
carrying a `schema/registry.ts` entry — one that is in the commander tree
but not the registry is invisible to the agents this surface exists for.
Both move verbs take the new parent as an optional positional rather than
a flag, because omitting it means the root, the one destination with no
id to spell; it goes over the wire as an explicit `null`, since the API
reads an absent `parentId` as "leave it alone" and dropping the field
would make the move a silent no-op that still reported success.

**One deliberate breaking change** (#1025):
`GET /api/v1/.../cells` now answers `400` for a non-sheet document where
it answered `404 Tab not found`. Nothing in the repository depended on
the old status — the CLI forwards the envelope verbatim and maps both to
the same exit code.

### Notifications

**The dropdown routes by type instead of by shape** (#1016). It had one
click-through mapper switching on whether a document row was attached
rather than on what happened, which made two of nine types wrong. A
workspace join carries no document, so the row marked itself read on
click and went nowhere — and its sentence named none of the workspaces
the reader belongs to. The row *stored* `workspaceId`; the list select
dropped it as something "the caller already knows", true of a document
notification and false of the one type with no document. A review-queue
nudge carries a document its recipient **cannot open** — a reviewer
belongs to neither the publishing workspace nor the document — and now
opens `/admin/templates`, the page the notification exists to make
someone open. One widening is stated where the next person will look: the
publishing workspace's name now reaches a non-member reviewer.

### Product — Docs

**Docs get the vertical rhythm their named styles described** (#1027).
Added after this document was drafted; see the window note at the top.

A plain meeting-notes document rendered as one undifferentiated column.
All 13 of its blocks carried an identical
`{marginTop: 0, marginBottom: 8, lineHeight: 1.5}` — headings included,
though `BUILTIN_STYLES` says a Heading 1 gets 27px of space-before.
Measured on screen, the ink gap above a heading was ~22px and below it
~21px, so the heading sat exactly halfway between the section it ended
and the one it introduced and proximity grouping collapsed.

**The cause was a seam, not a value.** `resolveStyleInline` resolved
lazily at layout time, but `resolveStyleBlock` was materialized eagerly
at write time — and its only per-edit production call site is
`setBlockType`, in the browser. A heading that arrived any other way —
DOCX or markdown import, paste, an `/api/v1` PUT, the CLI, a template, a
document copy — never got its spacing at all. Spacing now resolves lazily
too, which repairs every existing document at the next repaint with no
migration and no CRDT write.

Doing that safely required making "unauthored" representable, since a
value sentinel alone is wrong: Word writes `w:before="0"` for a
deliberate one-click zero, which must survive rather than be re-resolved
to the style's default.

### Fixes

- **Board sync died on the first element insert** (#1011). Inserting any
  element stranded the document: the sync chip went to "Not saved" and
  nothing that session reached the server again. `batch()` opens one
  `doc.update()`, the editor's insert commit selects the element from
  inside it, `Selection.notify()` is synchronous — so BoardView's
  listener wrote presence with a second, **nested** `doc.update()`. The
  SDK builds its ChangeContext from `doc.changeID` on entry and only
  advances on commit, so both changes get the same clientSeq; the pushed
  pack is `[1, 2, 2]`, the server refuses it, and `changeID` stays a step
  behind forever. `YorkieSlidesStore` had already solved this and says
  why in the comment on `activePresence`; the board store was ported from
  it and dropped that field. It gets the seam back.
- **A file viewer returns to the folder the document lives in** (#1013).
  The documents list keys its folder off a `?folder=<id>` query
  parameter, not a path segment, so `useDocumentsPath` always resolved to
  the workspace root and the back arrow lost the folder. The data was
  never missing — `GET /documents/:id` returns `folderId` and the viewer
  never passed it down. Prev/next neighbours are scoped to the folder
  too, since they were collected workspace-wide and the back destination
  derives from the *current* image, so walking into a neighbour silently
  moved where back would land.
- **The loading indicator is centred in every document type** (#1018).
  `Loader` declared no width, and every editor's canvas renders inside a
  row-flex `PreviewSurface`, so the loader was shrink-to-fit and pinned
  left — measured in a browser at 63 px inside a 1016 px surface, with
  its own `items-center` centring the spinner inside that collapsed box,
  which is what made it look intentional rather than broken. Three call
  sites had independently grown a centring wrapper and three more failed
  the opposite way in a column-flex parent. One `flex-1` fixes both,
  because `flex-basis` governs the main axis in either orientation.
- **Add link works at a caret inside a header or footer** (#1025). The
  menu row is offered on `!readOnly`, but its callback bailed silently
  when `getCursorScreenRect` resolved through the body layout with no
  header/footer branch — while the render path had branched to
  `computeHFCursorPixel` for exactly this case all along. Fixed by making
  it work rather than by gating it: `insertLink` reaches header blocks
  through `Doc.getBlock`, and the test asserting a header href passes
  against unmodified source. Only the anchor was missing.

### Security and hardening

- **A v1 document `PATCH` was a mass assignment** (#1019). The handler
  took an inline structural `@Body()` type, for which TypeScript emits
  `Object` as the metatype — so the global `ValidationPipe`, whose
  whitelist can only strip properties it sees on a DTO class, never
  engaged and the body reached `prisma.document.update` intact. A member
  or write-scoped key could rewrite `type`, rerouting which editor opens
  a document, or `fileId`, repointing a blob past the check its sibling
  route performs. **It survived a green suite because the existing spec
  called handlers directly**, which bypasses the pipe entirely.
- **Cell writes seeded a spreadsheet root against any document type**
  (#1019). A write to `tab-1` against a doc, note or slides id answered
  `200` and left a permanent invisible `sheet-<id>` Yorkie document that
  a later `GET` read back.
- **`packages/frontend/.env.production` was committed with production
  credentials** (#1014 found, #1019 fixed). It carried
  `https://api.wafflebase.io`, `https://api.yorkie.dev`, the upstream
  Yorkie public key and wafflebase's analytics property, and `vite build`
  runs in production mode where that file outranks the localhost `.env`
  beside it — so **every fork and self-host that built without overrides
  shipped a bundle addressing wafflebase's own service, silently**. It
  could not simply be deleted, because `publish-ghpage.yml` runs
  `build:all` with no overrides and that file *was* the hosted site's
  configuration. The values moved to repository variables rather than
  into the workflow, because a fork inherits no variables but does
  inherit workflow contents — hardcoding would have reproduced the bug in
  every fork's deploy.
- **`readBoundedInteger` returned the default for out-of-range input**
  (#1019), so `LAKEHOUSE_DUCKDB_THREADS=64` yielded **2 when 32 was
  theirs for the asking** — asking for more silently got you the
  minimum-ish default rather than the ceiling. Out of range now clamps; a
  malformed value keeps the default, since `"abc"` names no nearest
  bound.
- **28 Dependabot alerts cleared** (#1020) — 14 high / 13 medium / 1 low,
  every one patchable inside its current major line. Four sections
  totalling exactly 28 **alerts** (not pins — 8 alerts came from
  refreshing 4 stale `pnpm.overrides` pins: `fast-uri`, `qs`, and both
  `js-yaml` lines, each pinned to a version that had itself since become
  vulnerable). The other three sections: 10 direct dependency bumps, 4
  alerts closed by 3 new transitive overrides, and 6 in
  `scripts/agent/package-lock.json`, which carries a separate npm
  lockfile outside the pnpm workspace and so was never reached by the
  root overrides.

  `pdfjs-dist` is the only bump with real regression risk
  (GHSA-hq66-cqwq-w95j, arbitrary JS execution on opening a malicious
  PDF, and the viewer opens user-uploaded PDFs). Its unit test fully
  mocks `pdfjs-dist`, so it was verified separately — typecheck against
  the resolved declarations, the build still emitting cmap and
  standard-font assets, and a Node smoke against the exact build the
  viewer imports. Declared `^6.2.108`; **resolved 6.3.289**, which is
  the number to quote if one is quoted.

  The mechanism matters more than the fix: Dependabot security updates
  are **disabled** on the repository and there is no
  `.github/dependabot.yml`, so no automated PR has ever opened and every
  fix so far has been a hand-edited override pin. Enabling it is a
  repository setting that could not land in the commit — which is why
  half these alerts were stale pins in the first place.

### Docs and project hygiene

**A four-part audit against the code, and the code defects it found**
(#1014, #1019, #1021, #1023, #1024). The documentation described roughly
the v0.5 product while the app shipped v0.6.8.

What the homepage was advertising is the sharpest illustration. One card
promised that Docs reference Sheets cells inline — "your launch plan
reads $18,799 today and updates itself tomorrow" — when the block
vocabulary in `packages/docs/src/model/types.ts` has no embed or link
block, no design doc proposes one, and a repo-wide search returned that
marketing line as the only hit. A second promised an embeddable grid,
when every engine package is private and unpublished. The root README
still opened with "Early development … we are actively working on
DataSource integration" long after PostgreSQL datasources and the whole
lakehouse connector shipped, and advertised a **MySQL connector that has
never existed**.

Several pages could not be followed at all: four named menu items that
exist nowhere — two of them Import XLSX/DOCX/PPTX, which had been
collapsed into a single extension-routing door, and two more Upload PDF
and Upload Image; charts
and pivots were reached through an Insert menu the sheets toolbar does
not have; build-a-deck opened by telling you to double-click the title on
a new deck's first slide, which is Blank and has no placeholders. Some
were wrong in the *unsafe* direction: `sheets/datasources.md` said a
connection belongs to its creator and collaborators run their own, when
every handler gates on workspace membership alone and the query runs
against the creator's decrypted stored password. And the slides shortcut
table documented z-order keys that do not exist — inside a text box those
keys reach the docs editor and **outdent**, so following the page
actively mangles your slide.

P1 wrote five pages for subsystems with no page and no sidebar entry —
version history, templates, workspaces, conditional formatting, lakehouse
tables. Workspaces was the most overdue: nothing anywhere described
workspaces, membership, roles or invites, yet `collaboration.md` already
depended on the concept. Deriving its authority table from the guards
rather than from UI copy is how it ended up documenting two real gaps as
behaviour: there is no role change or ownership transfer at any layer,
and the workspace Name and URL fields are shown to members but rejected
server-side.

Counts were recomputed rather than restated: 55+ shapes is **137**
insertable kinds, the theme count is **23**, the formula catalog is **462
entries / 445 excluding operators**. An unverifiable "~85% of Google
Sheets" claim was dropped rather than reworded. `CLAUDE.md` got extra
care because every agent session loads it, so a wrong command there is
repeated indefinitely — the ANTLR command said `pnpm sheet` where the
script is `sheets`.

**The class of defect the audit kept finding is worth naming: a control
offered where its action silently no-ops.** The docs Insert comment row
(which needs both a selection and a signed-in user, where the menu
checked neither), the upload panel that never rendered `item.warning` so
CSV truncation reached the user only as a transient toast, the pivot
Filters area that writes no `hiddenValues`, and Add link at a header
caret. Three code follow-ups stay open, all three filed under
"needs design" in `20260904-audit-followup-code-defects-todo.md` — and
none of them is in that class, since the four examples just listed were
all fixed by #1019 or #1025. (An earlier draft said "nine … three of them
in that same class"; nine reconstructs only by counting still-open prose
bullets in the archived audit task, which no artifact states, and the
class claim contradicted its own examples.)

### A correction this release doc had to make to itself

An earlier draft of this section claimed v0.6.8's "`npm-publish` and
`docker-publish` green" box was **unsatisfiable** — that
`docker-publish.yml` fires only on pushes to `main` and so never produces
a version-named run. That was wrong, it was caught by this branch's own
claim audit, and it is recorded rather than quietly deleted because the
way it was reached is the more useful part.

`docker-publish.yml` has **two** triggers, and has since #803 landed
before v0.6.7. It waits on CI for `:latest` (the comment in the file
explains why: the old `push: main` trigger raced the run that decided
whether `main` was green, so a red `main` published anyway), *and* it
keeps a direct `release: types: [published]` trigger, because a release
publishes a tagged image without going through a CI-on-main run.
`gh run list --workflow=docker-publish.yml --event=release` lists a
successful run titled `v0.6.8`, and one for every release back to
v0.4.6.

**The error came from reading one unfiltered listing.** A bare
`gh run list --workflow=docker-publish.yml --limit 5` returns five runs
all titled "Docker Publish" — the `workflow_run` ones — because those are
far more frequent. Seeing no version-named run in that page, the draft
concluded none existed, and then generalized the absence into a claim
about the trigger without ever opening the workflow file. The file is
eight lines of comment explaining exactly this.

So v0.6.8's box was satisfiable, was satisfiable at the time, and its
run was green. The box above is restored to asking for both, with the
`--event=release` flag written into it so the next person does not
repeat the listing that caused this.

## Review

Written 2026-09-05, immediately after the rollout checks, which is the
rule v0.6.8's slip produced.

**The release shipped and is verified through the registries.** Tag
`v0.6.9` is annotated and on the merge commit, the GitHub Release is
Latest, both publish workflows ran green off the release trigger, npm
carries `0.6.9` with `dist-tags.latest` moved, and Docker Hub carries a
genuine multi-arch OCI index. The deployment pin is prepared and
verified but **not opened** — see below.

**Three things went wrong, and all three were caught by a box rather than
by noticing.** That is the useful result: the checklist earned its
existence three separate times in one sitting.

1. **#1027 landed in the merge queue ahead of #1028.** The rebase was
   clean and `main` was unmoved at push time; the other PR merged
   nineteen minutes later, while both sat in the queue. So the tag covers
   18 commits and this document had been drafted against 17. Caught by
   recounting after the merge and before the tag — the only step that
   *can* catch it, since nothing pre-push exists to. The GitHub Release
   notes cover #1027, and the counts here are recomputed rather than
   adjusted.

2. **A green `npm-publish` did not mean a published package.** The
   registry, queried directly the moment the workflow went green, still
   read `latest: 0.6.8` with no `0.6.9`. It was propagation lag rather
   than a failure — but the workflow status could not have told me that,
   and the box that says *confirm from the registries, not from the
   workflow logs* is the only reason the difference was ever examined.
   Refined into a rule: poll the registry, do not sample it once, and
   query `registry.npmjs.org` rather than `npm view`, which reads through
   a cache.

3. **The six-line devops bump nearly shipped as four.** BSD `sed` does
   not support `\s`, so the expression matched nothing, exited 0, and
   left the two bare `version:` labels at `0.6.8` — exactly the state
   #343 and #344 shipped and devops#346 had to fix. Caught by counting
   what should be gone (`grep -c '0\.6\.8'` must be 0) rather than by
   reading the four changes that looked right.

**And one thing this session could not finish.** The devops pin is
prepared and verified but the write to `yorkie-team/devops` was refused
by this session's permissions. That leaves the last two boxes open, which
means this task does **not** archive with the release — the same state
v0.6.8 was criticized for above, arrived at for a different and legitimate
reason. Recorded as blocked rather than left silently unticked, which is
the distinction that matters: v0.6.8's boxes were open because nobody
returned to them, these are open because the work has not happened.

**On the claim audit, in hindsight.** It killed eleven claims pre-merge,
one of which would have taught future releases to skip a working check.
The three failures above are all of the same family — a plausible reading
substituted for a measurement — and none of them was in the diff, so no
amount of reviewing the branch would have surfaced them. The generalizable
form is in the lessons file: **the checks that caught things were the ones
that produced a number, and the ones that missed were the ones that
produced an impression.**
