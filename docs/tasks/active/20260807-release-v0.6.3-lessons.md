# Release v0.6.3 — Lessons

## A filename pattern is a silent filter

`tasks-archive.mjs` matches `YYYYMMDD-<slug>-(todo|lessons).md` and ignores
everything else. `20260720-documents-bulk-select-move-plan.md` was named
`-plan.md`, so it was never a candidate for archiving — not "not yet done",
but invisible. It sat in `active/` for two weeks after merging as #503, and
no amount of re-running the script would ever have moved it. The audit found
it only because the file list was read directly instead of trusting the
script's output.

**Rule:** when a script decides what to act on by filename, audit the files it
*skipped*, not just the ones it reported on. A tool that silently drops
non-matching input reports success either way.

## "Not archived" and "not finished" are different states

The archive script keys on unchecked boxes, which conflates three things: work
genuinely in progress, work that shipped but was never ticked, and work whose
open items are decisions that will never be ticked. `generic-file-upload` had
77 unticked boxes and had shipped across three PRs with a complete Review
section. `yorkie-auth-webhook` has open items reading "NOT a code fix" and "by
design" — permanently unarchivable by construction.

**Rule:** before trusting a completion signal, check what it actually measures.
Read the Review/PR section of each task rather than the checkbox count.

## Do not tick a box to make a script happy

Two manual verification steps in `generic-file-upload` were genuinely skipped
for lack of a database, and the whole-branch review had already caught a defect
one of them would have found. Ticking them would have unblocked the archive at
the cost of a false record. They were converted to plain bullets marked
**SKIPPED** instead: the checkbox count reaches zero, the archive proceeds, and
the record still says the flow was never run by hand. Same treatment for the
bulk-select task's unrecorded manual e2e (`not recorded`) and its missing
lessons file, which was not reconstructed.

**Rule:** when a record and a gate disagree, change the gate's input shape, not
the record's truth value.

## Contributor lists do not carry over between releases

The release doc was first drafted with @ggyuchive in Contributors, carried over
from the v0.6.2 doc where they are credited as a contributing maintainer. They
have no commits in the `v0.6.2..v0.6.3` window. Git author names also do not
map to GitHub handles ("Taejung Kim" -> @te-ing, "Min-Ah Park" -> @fmaPark),
so `git log --format=%an` cannot produce a correct credits list on its own.

**Rule:** resolve contributors from
`gh api repos/.../compare/<prev>...<head> --jq '.commits[].author.login'` per
release. Never copy the previous release's list forward.

## A green publish workflow is not a published artifact

Both release workflows reported `success`. That is evidence the job exited
zero, not that the package is installable or the image pullable. Both were
confirmed directly — `npm view @wafflebase/cli version` and the Docker Hub tag
API — before the checklist was marked done.

**Rule:** verify the artifact at its destination, not the job that was supposed
to put it there.

## Generated code goes stale without an install

`pnpm build` failed on `fileSize does not exist in DocumentCreateInput` with no
defect in the source. `schema.prisma` had gained the column in `fe9e20a40`, but
the generated client in `node_modules` predated it: the backend's
`postinstall: prisma generate` only fires on install, so pulling a schema
change without a subsequent `pnpm install` leaves a stale client behind.

**Rule:** a type error naming a field that plainly exists in the schema is a
regeneration problem, not a code problem. Check the generated artifact's
freshness before editing anything.

## An unchecked box is not evidence about a system the doc cannot see

The v0.6.2 release doc carries its devops image-pin step unchecked. That was
read as "the pin was never bumped" and written into this release's doc, into
PR #706, and into an earlier draft of these lessons as "the skew is now two
versions wide". All of it was wrong. The devops repo had bumped to v0.6.2 in
`e0b75a7` (#332); `k8s/wafflebase/deployment.yaml` was already pinned at v0.6.2.
Only the task doc was stale — the step happened in a repo the doc has no way
to observe.

This is the same class of error as `documents-bulk-select-move`, but pointing
the other way: there, a shipped task looked unfinished because of a filename;
here, a finished out-of-repo step looked open because nobody came back to tick
it. Both were read off checkbox state instead of the system.

**Rule:** for a checklist item whose work lands outside this repo, verify it
where it actually happens before repeating its status. `git log` in the target
repo is one command, and it outranks any box.

## The deploy is not the release

Frontend auto-ships on `main` via Pages; the backend image is pinned by hand in
a separate repo, so the release is not deployed when the tag is cut. This is
the skew that broke document open in #469.

**Rule:** a release checklist item that lives in another repo will not complete
itself. Treat its being open as a reason the release task stays active — and
re-verify it at the source rather than carrying the previous release's status
forward.
