디자인 에디터 · 디버그 리포터 실행 방법

두 도구를 각자 환경에서 처음부터 끝까지 한 번씩 돌려봅니다. 화면에서 무언가를 바꿔 PR까지, 화면에서 무언가를 발견해 리포트 번들까지. 명령을 그대로 따라 치면 되고, 각 단계마다 무엇이 보여야 정상인지를 함께 적어 두었습니다.

시작 전 세션 진행 준비물 확인 파트 A — 디자인 에디터 무엇을 하는 도구인가 A1. 띄우기 A2. 화면 익히기 A3. 클래스 바꾸기 A4. 토큰 바꾸기 A5. 코드로 저장 A6. PR 열기 A7. 되돌리기 A8. 증상 표 파트 B — 디버그 리포터 무엇을 하는 도구인가 B1. 앱 띄우기 B2. 켜기 B3. DOM 대상 잡기 B4. 캔버스 대상 잡기 B5. 사라지는 상태 B6. 리전 드래그 B7. 취소 동작 B8. 리뷰 패널 B9. 넘기기 B10. 인테이크 B11. 증상 표 그다음 내 프로젝트에 붙이기 치트시트

세션 진행

00:00준비물 확인 — Node·git·클론. 여기서 막히는 사람이 있으면 먼저 해결하고 갑니다.
00:10파트 A · 디자인 에디터 — 띄우기 → 클래스/토큰 편집 → 코드로 저장 → PR
00:45파트 B · 디버그 리포터 — 앱 띄우기 → 캡처 4가지 → 리뷰 → 넘기기 → 인테이크 관찰
01:20정리 — 각자 만든 PR/번들 훑어보기, 자기 프로젝트에 붙이는 이야기
세션 전에 한 번 돌려 오시면 좋습니다. 첫 실행은 의존성 설치에 약 2분이 걸리고, WSL2/네트워크 드라이브에서는 첫 씬 로드가 1분 가까이 걸립니다(의존성 최적화 단계이며 멈춘 게 아닙니다). 두 번째 실행부터는 몇 초입니다. pnpm design 한 번만 미리 실행해 두면 세션에서 기다릴 일이 없습니다.

준비물 확인

아래 네 가지가 전부입니다. pnpm, Docker, 데이터베이스, GitHub CLI는 필요하지 않습니다 — 스크립트가 준비해 주거나, 없어도 동작하는 경로가 있습니다.

필요한 것확인 명령없다면
Node 22 이상node --versionnodejs.org의 LTS 설치
Gitgit --versiongit-scm.com
커밋에 쓸 이름과 주소git config --get user.name
git config --get user.email		두 줄이 모두 출력되어야 합니다. 하나만 있으면 커밋이 안 됩니다.
git config --global user.name "이름"
git config --global user.email "you@example.com"
저장소 클론—git clone https://github.com/wafflebase/wafflebase.git

왜 identity를 따로 확인하나 — wafflebase의 user.name은 저장소 로컬 설정에 들어 있는 경우가 많습니다. 즉 새로 클론하면 identity가 없는 상태이고, IDE로만 git을 써 온 사람도 대부분 그렇습니다. PR 스크립트는 이걸 대신 채워 넣지 않습니다 — 본인이 고르지 않은 이름으로 커밋되는 것이 커밋이 안 되는 것보다 나쁘기 때문입니다.

Part A디자인 에디터란

앱의 실제 라우트를 실제 컴포넌트 소스로 렌더링해 보여주고, 화면에서 고친 것을 내 디스크의 .tsx와 토큰 소스에 다시 써 넣는 dev 전용 Vite 플러그인입니다. 목업이 아니라 커밋된 코드가 하는 일을 보는 것이고, 리뷰 화면은 git diff입니다.

이 도구는 당신의 워킹 트리에 파일을 씁니다. 그게 이 도구의 목적입니다. 다만 root 밖으로 나가는 쓰기는 전부 거부되고, 백업은 소스 옆이 아니라 node_modules/.cache/wafflebase-design-editor/에 남습니다. 실습 전에 작업 중인 변경사항이 있다면 커밋하거나 stash 해 두세요.

백엔드·DB·Docker가 필요 없는 이유 — 씬들은 자기 데이터 요청을 fixture로 답하고, 프레임 밖으로 나가는 네트워크 요청은 차단됩니다. wafflebase에서 단독으로 실행되는 유일한 부분입니다.

A1. 띄우기

  1. 저장소 폴더에서 한 명령

    # 저장소 루트에서
pnpm design

# pnpm이 아직 없다면 — 같은 일을 하고, pnpm도 준비해 줍니다
node scripts/design.mjs

    왜 pnpm --filter … dev가 아닌가 — 에디터 UI(셸)는 소스가 아니라 프리빌드된 번들에서 서빙됩니다. 원시 dev 명령은 어제 빌드된 셸을 오늘 코드에 대고 아무렇지 않게 띄워 줍니다. pnpm design은 mtime을 비교해 필요할 때만 다시 빌드하고, 이미 된 단계는 전부 건너뜁니다.

  2. 출력에서 이 두 줄을 읽습니다

    ✓ dependencies installed ✓ editor shell built ✓ @wafflebase/core built ✓ the design editor is at http://localhost:5173/__design-editor/ [design-editor] editing /home/you/wafflebase — open /__design-editor/ VITE v6.4.3 ready in 551 ms
    확인editing 뒤의 경로가 내가 편집하려는 그 저장소인지. 클론이 여러 개거나 worktree를 쓰고 있다면 여기서 멈추고 확인하세요. 이게 다르면 나중에 git diff가 비어 보입니다.
    확인포트는 5173이 아닐 수 있습니다. 이미 쓰는 프로세스가 있으면 Vite가 다음 포트를 잡고, 실제로 출력된 주소가 정답입니다.

  3. 설정이 제대로 물렸는지 한 번에 보기

    curl -s localhost:5173/__design-editor/api/health | jq
    { "ok": true, "root": "/home/you/wafflebase", "scenes": ".../packages/design-sandbox/scenes.config.json", "providers": ".../packages/design-sandbox/src/scenes/providers.tsx", "tokens": "configured", "aliases": [{ "find": "@", "replacement": "packages/frontend/src" }, "…"] }

    화면이 뜨긴 했는데 뭔가 이상할 때 가장 먼저 볼 곳입니다. 씬을 디버깅하기 전에 “내 설정이 실제로 연결됐나”를 먼저 답해 줍니다.

URL 세 개

URL무엇인가
/__design-editor/여기를 엽니다. 3-pane 에디터 셸.
/__design-editor/scene?scene=<id>&frame=<side>&theme=light씬 하나만 프레임 없이. 특정 씬이 이상하게 굴 때 크롬 없이 보고 싶을 때.
/__design-editor/api/health플러그인이 실제로 해석한 설정.
/404가 정상입니다. 이 dev 서버는 wafflebase 앱이 아니라 에디터의 네임스페이스를 서빙합니다.

A2. 화면 익히기

왼쪽 · 무엇을 보고 있나

Components — 디자인 시스템의 조각 하나(버튼, 카드, 메뉴). Primitives와 App components로 나뉩니다.

Scenes — 실제 앱의 페이지 한 장(문서 목록, 로그인, 설정). 총 11개 중 10개가 마운트되고, pdf-viewer는 deferred로 비활성 표시됩니다.

가운데 · 실물

빈 배경을 드래그하면 이동, Ctrl/⌘+스크롤로 포인터 기준 확대.

위쪽 버튼들: Pick(프레임 클릭이 선택으로 동작하게), Mock data(리스트 fixture를 비워 빈 상태를 보기), 뷰포트 폭, 새로고침.

오른쪽 · 무엇을 바꿀 수 있나

Layout — 화면에 있는 것의 구조. 행을 클릭하면 그 조각이 선택되고, 옆에 간격·크기·정렬 편집기가 뜹니다.

Bindings(컴포넌트 모드에서만) — 이 컴포넌트의 각 부분이 어떤 토큰을 쓰는지.

Tokens — 토큰 자체의 값. 여기를 바꾸면 그 토큰을 쓰는 모든 것이 따라옵니다.

확인씬을 하나 열고 왼쪽 목록과 가운데 화면이 같은 이름인지. 미리보기는 바뀌는데 “페이지가 그대로”라고 느껴진다면 대개 생각하던 씬과 다른 씬을 보고 있는 것입니다.

A3. 실습 — 클래스 하나 바꾸기

  1. 씬을 하나 엽니다

    Scenes 모드에서 documents나 login처럼 요소가 뚜렷한 씬이 좋습니다.

  2. Pick을 켜고 프레임 안의 요소를 클릭합니다

    Pick이 꺼져 있으면 클릭은 그 요소를 실제로 누르는 동작이 됩니다(버튼이면 눌립니다). 오른쪽 Layout 아웃라인에서 행을 클릭해도 같은 선택이 됩니다.

    확인선택되면 그 노드 옆에 작은 클래스 편집기가 뜨고, 오른쪽 아웃라인의 해당 행이 선택 표시됩니다. 아웃라인이 비어 있다면 그 씬의 파일이 매니페스트의 components에 없어서 소스 앵커가 없다는 뜻입니다.

  3. 클래스를 바꿉니다 — 예: 패딩이나 색 유틸리티

    확인프레임이 즉시 바뀝니다. 아직 파일에는 아무것도 쓰지 않았습니다. 헤더의 Save to Code 옆 숫자가 1 늘어납니다.

    미리보기가 아무 스타일도 안 먹는다면 — 런타임에 조합된 클래스는 Tailwind의 스캔 대상에 없으면 규칙 자체가 생성되지 않습니다. 에디터는 이런 후보들을 등록해 두지만, 거절되거나 상한에 걸린 클래스는 규칙이 없어 아무것도 안 보이는 상태로 렌더됩니다.

  4. ⌘/Ctrl+Z, ⇧+⌘/Ctrl+Z로 스테이징을 되돌려 봅니다

    저장 전 편집은 스택으로 쌓입니다. 헤더의 Undo / Redo / Reset도 같은 스택을 다룹니다.

A4. 실습 — 토큰 값 바꾸기

  1. 오른쪽 Tokens 탭으로 갑니다

    색은 클래스가 아니라 토큰입니다 — primary 같은 이름이 있고, 각 부분이 어떤 이름을 쓰는지가 정해져 있습니다.

  2. 토큰 하나의 값을 바꿉니다

    확인그 토큰을 쓰는 모든 것이 한 번에 따라 움직입니다. 한 요소만 바뀌었다면 토큰이 아니라 그 요소의 클래스를 바꾼 것입니다.

    미리보기가 어떻게 진짜인가 — wafflebase의 토큰은 TypeScript const에 살고, 앱이 쓰는 CSS는 생성물입니다. 그래서 미리보기는 패치된 소스 텍스트를 받아 실제 에미터를 그대로 돌려서 변수 맵을 만듭니다. 저장이 쓸 결과와 미리보기가 어긋나지 않게 하는 것이 이 워커의 존재 이유입니다.

  3. 라이트/다크를 토글해 봅니다

    헤더의 Dark 버튼. 테마별 값이 따로 있는 토큰이라면 한쪽만 바뀌는 것이 정상입니다.

A5. 코드로 저장

  1. 헤더의 Save to Code를 누릅니다

    버튼에 스테이징된 변경 개수가 표시됩니다. 누르면 리뷰가 열립니다 — 지금 모습과 바뀔 모습을 나란히, 그 아래에 파일별로 실제로 바뀔 줄들.

  2. 승인합니다

    확인승인 전에는 아무것도 쓰이지 않습니다. 승인하면 변경은 내 컴퓨터의 저장소 파일에 들어가고, 그 이상 어디에도 가지 않습니다.

  3. 어디에 썼는지 두 곳에서 확인합니다

    • 쓰기 로그(헤더의 두루마리 아이콘, 옆에 개수) — 이번 세션에 쓴 것 전부를 최신순으로, 어느 파일에 떨어졌는지까지. 저장 시 뜨는 토스트는 사라지지만 이건 남습니다.
    • ⓘ 버튼 — Editing, 즉 에디터가 쓰는 폴더. 클론이 여러 개일 때 이것이 기준입니다.

  4. 터미널에서 확인합니다

    git diff

    색 변경은 대개 packages/core/src/tokens/에, 한 컴포넌트에 국한된 변경은 그 컴포넌트 파일에 떨어집니다.

    git diff가 비어 있다면 거의 확실히 다른 클론을 보고 있는 것입니다. 에디터 헤더의 ⓘ를 눌러 Editing 경로를 읽고, 그 폴더에서 다시 확인하세요.
에디터는 켜 둔 채로 다음 단계로 갑니다. PR 스크립트는 실행 중인 서버가 들고 있는 “무엇을 썼는지” 기록을 읽습니다. 닫아도 PR은 만들 수 있지만, 커밋 범위가 워킹 트리 전체로 넓어지고 설명이 부정확해집니다.

A6. PR 열기

  1. 두 번째 터미널에서, 같은 폴더에서

    # 무엇을 할지만 보여주고 아무것도 바꾸지 않습니다
pnpm design-pr --dry-run

# 실제로
pnpm design-pr

    만들 브랜치, 커밋할 파일, 제목을 먼저 출력하고 진행합니다. 에디터가 바꾼 파일만 커밋합니다 — 다른 작업 중인 변경은 목록에 나열되고 그대로 둡니다.

  2. 내 환경이 어느 경로인지는 스크립트가 판단합니다

    조건결과
    rung 3GitHub CLI + 푸시 권한브랜치·커밋·푸시·PR 생성까지. 주소를 출력하고 브라우저를 엽니다.
    rung 2GitHub CLI, 권한 없음대부분 여기입니다. 포크를 만들어 거기에 푸시하고 원본으로 PR을 엽니다(첫 회 확인을 묻습니다).
    rung 1GitHub CLI 없음브랜치를 푸시하고 GitHub의 compare 페이지를 브라우저로 엽니다 — 내용이 채워진 폼이라 초록 버튼만 누르면 됩니다.
    rung 0git 없음 / origin 없음그렇게 말하고 멈춥니다. 복사한 폴더가 아니라 git clone으로 받으세요.

    왜 rung 1이 있나 — gh auth login을 전제로 하면 이 도구가 존재하는 이유인 사람(코드를 안 쓰는 디자이너)이 첫 계단에서 멈춥니다. 브라우저 하나만 있으면 끝나는 경로가 반드시 있어야 합니다.

  3. 설명을 더 낫게 쓰고 싶다면

    기본 설명은 에디터의 편집 기록에서 뽑아낸 것이라 정확하지만 건조합니다. Claude Code가 있다면:

    Open a PR for my design changes

    같은 기록과 실제 diff를 읽고 제목·본문을 쓴 뒤 같은 스크립트에 넘깁니다. 직접 줄 수도 있습니다:

    pnpm design-pr --title "Soften the primary button's hover" --body-file notes.md

절대 하지 않는 것 (관례가 아니라 보장)

  • main에 커밋하지 않습니다 — 항상 브랜치를 만듭니다.
  • 에디터가 바꾸지 않은 파일은 커밋하지 않습니다.
  • force-push 하지 않고, 기존 브랜치를 덮지 않습니다.
  • 비밀번호나 토큰을 저장하지도, 묻지도 않습니다. git과 gh는 이미 내 머신에 있는 자격증명으로, 나로서 실행됩니다.

A7. 되돌리기

  • 저장 전 — 에디터의 ⌘/Ctrl+Z, 또는 헤더의 Reset.
  • 저장 후, PR 전 — 쓰기 로그에서 파일 목록을 확인하고 git checkout -- <파일>. 또는 에디터의 Undo가 브리지를 통해 파일을 되돌립니다.
  • 실습을 깨끗이 끝내려면 — git status로 남은 변경을 확인하고 정리하면 됩니다. 백업은 소스 옆이 아니라 node_modules/.cache/에 있으므로 저장소를 더럽히지 않습니다.

A8. 증상 표 — 파트 A

보이는 것원인 / 조치
모든 씬이 mount error씬이 필요한 빌드 산출물이 없습니다. pnpm design이 알아서 만들어 줍니다 — 다른 방법으로 서버를 띄웠다면 pnpm design으로 다시 시작하세요. 새 클론에서 나오는 증상입니다.
셸은 뜨는데 프레임이 no scene "<id>" in the scene manifest그 씬이 deferred이거나 매니페스트에 그 id가 없습니다.

콘솔에 unmocked request씬이 fixture 없는 데이터를 요청했습니다. 요청이 프레임 밖으로 나가는 일은 없으며, fixture를 추가하는 것이 맞는 조치입니다.

컴포넌트가 “needs app context”라고 합니다혼자 세울 수 없는 조각입니다(메뉴 항목엔 메뉴가 필요). 부모 컴포넌트를 여세요.

Part B디버그 리포터란

돌아가는 앱 위에 얹히는 dev 전용 리포팅 오버레이입니다. 단축키를 누르고, 잘못된 것을 가리키고, 한 문장으로 말하고, 몇 개 모아서 한 번에 넘깁니다. 에이전트가 이슈 문안과 “이 배치가 어떻게 PR로 쪼개지는지”에 대한 제안을 쓰고, 사람이 확정한 뒤에야 파이프라인이 검증하고 착지시킵니다.

사람이 하는 것

가리키기, 한 문장, 그리고 판단 — 문장 고치기, 항목 빼기, 그룹 조정, 확정.

사람이 하지 않는 것

파일 경로, 재현 절차, 라벨. 그 문장이 나중에 커밋 메시지의 “왜”로 그대로 들어갑니다.

파이프라인이 하지 않는 것

스스로 아무것도 열지 않습니다. 인테이크 스크립트 어느 것도 브랜치·커밋·이슈·PR을 만들지 않습니다.

버그만 보고하는 도구가 아닙니다. 항목의 종류는 spacing·color·token·copy·a11y·affordance·layout·logic 여덟 가지이고, 명백한 버그는 그중 logic 하나입니다. “간격이 좀 좁아 보인다”, “이 문구가 어색하다”, “여기 버튼 하나 있으면 좋겠다”가 전부 정상적인 리포트입니다. 실습에서도 그런 걸 잡으세요 — 버그를 찾아내야 한다고 생각하면 아무도 아무것도 못 잡습니다.

프로덕션에는 아예 없습니다 — 마운트가 import.meta.env.DEV로 정적 치환되므로 배포 번들에 코드 자체가 들어가지 않습니다. “비활성”이 아니라 “부재”입니다.

B1. 앱 띄우기

권장 — 인프라 없이

pnpm frontend dev

그런 다음 아래 라우트로 갑니다. 로그인도, 백엔드도, Docker도 필요 없습니다. 캔버스 개수가 서로 달라서 이 조합이 실습용으로 좋습니다.

라우트캔버스실습에서 쓰는 이유
/harness/hunt?surface=sheet2그리드+오버레이 두 레이어가 한 박스를 공유 — 합성 캡처와 셀 주소
/harness/docs12캔버스가 세로로 쌓여 있음 — 이음새를 넘는 리전 실습
/harness/hunt?surface=slides1단일 캔버스
/login0순수 DOM 경로

전체 앱으로 하고 싶다면

docker compose up -d   # PostgreSQL + Yorkie
pnpm dev              # 프론트(:5173) + 백엔드(:3000)

선택 — 드래프팅 키

에이전트가 초안을 쓰게 하려면 dev 서버 프로세스가 자격증명을 볼 수 있어야 합니다(ANTHROPIC_API_KEY, ANTHROPIC_AUTH_TOKEN, 또는 ant auth login). 없어도 실습은 전부 됩니다 — 초안 없이 내 문장 그대로 넘어가고, 항목당 PR 1개가 됩니다.

키는 브라우저에 절대 도달하지 않습니다. 드래프팅은 dev 서버 엔드포인트이고, 요청에 tools 파라미터 자체가 없습니다 — 출력 전용입니다. 씬 프레임은 앱 코드를 돌리는 곳이라, 거기서 읽히는 키는 모든 의존성에 노출된 키입니다.

B2. 켜기

Mod+Shift+Y 디버그 모드 켜기/끄기 c 캡처 r 리전 드래그 v 리뷰 패널 Esc 한 겹씩 벗기
확인떠 있는 배지에 c capture · r region · v review · Esc가 보이고, 포인터를 따라 아웃라인이 항상 그려집니다. 배지가 현재 바인딩의 정답입니다.

왜 Mod+Shift+Y인가 — 엔진들의 단축키 카탈로그와 브라우저가 예약한 조합을 모두 피한 조합입니다. 그리고 디버그 모드가 꺼져 있을 때도 동작해야 하는 유일한 바인딩이라 수식 키가 붙은 것도 이것뿐입니다. 나머지 한 글자 키들은 모드가 켜져 있을 때만 반응하고, 텍스트 필드에 포커스가 있으면 필드가 키보드를 가져갑니다.

B3. 실습 — DOM 대상 잡기

  1. /login이나 헤더의 버튼 위에 포인터를 둡니다

  2. c를 누릅니다 — 클릭하지 않습니다

    확인아이콘 위에서 눌러도 아이콘의 <svg>가 아니라 버튼이 잡힙니다. 컨트롤을 가리켰다는 것은 그 컨트롤을 말한 것이기 때문에, 의미 있는 가장 가까운 조상으로 승격합니다.

  3. 한 문장을 쓰고 Enter

    예: “이 버튼의 좌우 패딩이 옆 버튼보다 좁아 보인다.” 파일도, 재현 절차도 쓰지 않습니다.

    확인배지의 개수가 1 늘어납니다. DOM 대상은 사진으로 찍지 않습니다 — 셀렉터, 박스, 텍스트 발췌로 기술됩니다. 그게 에이전트가 소스를 grep하는 열쇠입니다.

B4. 실습 — 캔버스 대상 잡기

  1. /harness/hunt?surface=sheet로 가서 셀 하나 위에 포인터를 둡니다

  2. c

    확인대상이 의미 있는 주소(예: Sheet1!C7)로 잡힙니다. 시트 전체를 찍은 1280×721 사진이 아니라.
    확인캡처 이미지에 그리드와 선택 표시가 둘 다 들어 있습니다.

여기가 이 도구의 존재 이유입니다. 접근성 트리는 캔버스 안을 보지 못하고, 히트테스트도 답을 주지 못합니다 — 두 시트 캔버스는 pointer-events: none이고 이벤트는 감싸는 div가 처리하기 때문에, 그리드 한가운데에서 elementsFromPoint는 div 4개와 캔버스 0개를 돌려줍니다. 그래서 로케이터는 DOM을 질의해 캔버스를 찾고, 어느 셀인지는 마운트된 엔진에게 묻습니다. 엔진 로케이터가 답하지 못하면 컨테이너를 통째로 찍는 대신 커서 주변의 작은 리전으로 내려갑니다.

B5. 실습 — 사라지는 상태 보고하기

  1. 툴팁이 뜨는 곳에 포인터를 올려 둡니다. 또는 드롭다운을 열어 둡니다.

  2. 포인터를 움직이지 말고 c

    확인툴팁이 살아 있는 채로 캡처됩니다. 캡처가 끝난 뒤에 문장 입력창이 열리므로, 그다음에 상태가 무너져도 상관없습니다.

이것 때문에 트리거가 클릭이 아니라 키가 됐습니다. 호버 툴팁, 열린 메뉴, 진행 중인 드래그는 가리키기 위해 요구되는 그 클릭이 파괴합니다. 게다가 오버레이가 포인터 이벤트를 가로채면 아래 앱이 호버 추적을 멈추고 진행 중이던 드래그의 mouseup도 못 봅니다. 그래서 오버레이는 idle에서 포인터를 수동으로만 관찰하고(preventDefault·stopPropagation 없음), 키만 capture 단계에서 가로챕니다. 키는 포인터를 움직이지 않습니다.

남아 있는 한계 — 커서에서 떨어진 곳에 그려지는 툴팁을 조준하는 것은 여전히 안 됩니다. 포인터를 움직이는 행위 자체가 그걸 없애기 때문입니다. 프레임을 얼려서 그 안에서 조준하는 방법뿐인데, DPR 2에 캔버스 12개인 화면에서는 싸지 않아 보류돼 있습니다.

B6. 실습 — 리전 드래그

  1. /harness/docs로 갑니다 (캔버스 12개가 세로로 쌓여 있습니다)

  2. r를 누르고, 페이지 이음새를 가로지르도록 드래그합니다

    확인캡처된 이미지의 아래쪽이 검지 않습니다. 사각형과 교차하는 캔버스를 모두 합성하기 때문입니다 — 중심이 어디 들어 있는지로 고르면 이음새를 보고하려던 사람이 이음새가 빠진 증거를 첨부하게 됩니다.

  3. /login처럼 캔버스가 0개인 화면에서도 r로 드래그해 봅니다

    확인좌표만 남지 않습니다 — 사각형과 교차하는 의미 있는 요소들의 목록(셀렉터 + 텍스트 발췌)이 기록됩니다.

B7. 실습 — 취소는 무엇을 버리나

이 도구의 규칙 하나를 직접 확인하는 단계입니다. 리포트를 잃는 도구는 아무것도 안 하는 것보다 나쁩니다 — 보고자는 접수됐다고 믿고, 다음 관찰은 아예 하지 않게 되니까요.

  1. 문장 입력 중에 Esc

    확인그 항목만 버려지고 디버그 모드는 그대로입니다. 조준 상태로 돌아옵니다.

  2. 빈 문장으로 저장을 시도합니다

    확인저장 컨트롤이 눈에 보이게 비활성이고 이유를 말합니다. 조용히 삼키고 버리지 않습니다.

  3. Esc를 계속 눌러 봅니다

    한 겹씩 벗겨집니다: 패널 → 대기 중인 항목 → 리전 모드 → 디버그 모드. 한 번에 다 닫히지 않는 것은, 사라지는 줄 몰랐던 작업을 한 키로 날리지 않기 위해서입니다.

B8. 리뷰 패널

서너 개쯤 모았으면 v를 눌러 Debug reports 패널을 엽니다.

  • 문장과 제목을 고칩니다. 드래프팅 키가 있으면 에이전트가 쓴 초안이 채워져 있고, 없으면 내 문장이 그대로 있습니다. 어느 쪽이든 편집 가능한 초안이며 내가 저자입니다.
  • 썸네일이 동의 게이트입니다. 나갈 이미지를 전부 여기서 봅니다.
  • 처리 방식 세 가지 — Verify(재현해 보고 성립하면 PR) · File it(리플레이 없이 이슈로) · Drop(이건 보내지 않음).
  • agent:candidate 체크는 의도를 기록합니다. 자동 기여 게이트는 봇이 아닌 작성자를 요구하므로 라벨만으로 열리지 않고, 그래서 이 체크가 게이트를 약화시키지도 않습니다.
  • Proposed pull requests — 제안된 그룹에서 항목을 떼어내기(detach), PR 쪼개기(split), 두 PR 합치기(merge). 파일 이름은 UI에 나오지 않습니다. 서로 다른 종류를 합치면 막지는 않고 경고합니다.

무엇이 같이 묶이나 — 개수가 아니라 동질성이 기준입니다. 패딩 수정 둘은 같이 통과하거나 같이 떨어지지만, 패딩 수정과 수식 엔진 버그는 그렇지 않습니다. 그래서 spacing·color·token·copy·a11y는 같은 종류끼리, layout은 같은 파일 안에서만, logic은 절대 묶지 않습니다 — 하나가 막혔다고 나머지를 붙잡아 둘 이유가 없기 때문입니다. 한 항목은 한 커밋이라, 리뷰어가 커밋 하나를 빼면 리포트 하나를 거절할 수 있습니다.

B9. 넘기기

  1. 패널 아래의 Hand over N report(s)

    확인빈 문장이 남아 있으면 버튼이 비활성이고 몇 개가 비었는지 말해 줍니다. 초안을 기다리는 중이라도 보낼 수 있습니다 — 모델은 의존성이 아닙니다.

  2. 디스크에서 확인합니다

    ls .wb-reports/
cat .wb-reports/<session>/bundle.json | jq '.items[] | {note, target: .target.kind}'

    캡처 이미지는 번들 옆에 별도 파일로 저장됩니다 — 번들은 작게 유지되어야 하고 이미지는 메가바이트 단위이기 때문입니다.

    확인한 세션에서 두 번 넘기면 bundle.json 다음에 bundle-2.json이 생깁니다. 덮어쓰지 않습니다 — 보냈다고 말해 놓고 앞의 배치를 지우는 것은 이 기능이 가장 피하려는 실패입니다.

B10. 인테이크 — 이 배치가 어떻게 처리되는가

세션에서는 1단계만 직접 실행해 보고, 나머지는 표로 훑습니다. 어떤 스크립트도 스스로 PR이나 이슈를 열지 않습니다.

DIR=.wb-reports/<session>

# 1. 행동할 수 없는 번들은 거부한다. 이 다음 단계부터는 커밋을 만들 수 있다.
node ./scripts/agent/report-bundle.mjs "$DIR" --check

Claude Code를 쓴다면 전체 흐름은 명령 하나입니다:

/report-intake            # 기본값: .wb-reports/ 중 가장 최근 디렉터리
단계하는 일하지 않는 일
report-bundle번들을 fail-closed로 읽고 검증고쳐 주지 않음 — 이해 못 하는 번들은 거부
report-prior레포의 열린 이슈를 사전 리포트로 읽음판단·쓰기 없음
report-intake비밀 정보 마스킹, 중복 판정, 목적지 라우팅, 계획 생성실행·파일링 없음. 목적지는 삭제가 아님
report-verify각 항목의 검증이 무엇을 뜻하는지 계산레인을 직접 돌리지 않음(브라우저·Docker가 필요)
report-to-prPR 조립, 강제 분할/병합, 델타 기록프로세스를 하나도 띄우지 않음
report-back결과를 번들 옆에 기록 — 조정마다 이유까지해석하지 않음

여기서 눈여겨볼 두 가지

  • 제안은 계약이 아닙니다. 브라우저는 어떤 파일이 바뀔지 모릅니다. 그래서 두 방향으로만 조정됩니다 — 파일이 겹치면 강제 병합(전이적: A–B가 겹치고 B–C가 겹치면 셋이 한 PR), 종류가 잘못 잡혔으면 강제 분할. 분할은 항상 안전하고 병합은 아닙니다. 그리고 조정은 절대 조용히 일어나지 않습니다 — “제안 2 PR → 실제 3 (…이유…)”가 결과로 돌아옵니다.
  • 검증 실패는 리포트를 삭제하지 않습니다. “재현되지 않음”이 “관찰이 틀렸다”는 뜻은 아니므로, 목적지를 낮출 뿐입니다 — 기대한 바와 실패한 리플레이를 함께 이슈로 남겨, 불일치를 기계가 아니라 사람이 보게 합니다.

중복 판정에 척도가 두 개인 이유 — 리포트는 한 문장이고 이슈 본문은 여러 문단입니다. 포함(containment) 기준으로는 긴 이슈가 짧은 문장의 단어를 담고 있기만 해도 1.0이 나와서, 멀쩡한 리포트가 엉뚱한 이슈의 코멘트로 사라집니다. 그래서 리포트↔이슈는 Dice, 리포트↔장부는 포함을 씁니다.

B11. 증상 표 — 파트 B

보이는 것원인 / 조치
Mod+Shift+Y에 아무 반응이 없습니다프로덕션 빌드를 보고 있거나(오버레이는 dev에만 존재), 텍스트 필드에 포커스가 있습니다.
c·r가 앱의 입력에 그대로 타이핑됩니다정상입니다. 포커스된 텍스트 필드가 키보드를 소유합니다 — 이름 바꾸기 창에 “chart”를 치면 “hat”이 되던 문제 때문에 만든 규칙입니다.
아웃라인은 보이는데 캡처가 시트 전체를 찍습니다엔진 로케이터가 답하지 못한 경우입니다. 커서 주변의 작은 리전으로 내려가는 것이 설계된 동작입니다.
캡처 아래쪽이 검게 나옵니다이음새를 넘는 리전이 한쪽 캔버스만 합성한 경우 — 그게 고쳐진 동작이므로, 보이면 리포트감입니다.
패널에 “capture가 밀려났다”는 내용이 보입니다용량 가드가 가장 오래된 캡처부터 지웁니다. 항목 자체는 남습니다 — 중요한 건 문장이고, 무엇이 사라졌는지는 확정 전에 알려 줍니다.
초안이 not-configured로 나옵니다dev 서버 프로세스에 모델 자격증명이 없습니다. 정상 동작이며, 내 문장 그대로 넘어가고 항목당 PR 1개가 됩니다.
.wb-reports/가 없습니다아직 Hand over를 누르지 않았거나, 프론트엔드 dev 서버가 아닌 다른 서버로 열었습니다.

// 소비자의 vite.config.ts
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'
import { designEditor, cssVariables } from '@wafflebase/design-editor'

export default defineConfig({
  plugins: [
    react(),
    designEditor({
      root:      process.cwd(),         // 쓰기 경계 — 이 밖으로는 쓰지 않는다
      scenes:    'design/scenes.json',  // 어떤 라우트가 편집 가능한가
      providers: 'design/providers.tsx',
      tokens:    cssVariables({ stylesheet: 'src/index.css' }),
    }),
  ],
})
지원 범위
번들러Vite 6+ (dev 서버만)
프레임워크React 19, JSX/TSX 소스
스타일Tailwind v4 (클래스 편집에 필요. 토큰 편집만이면 필수는 아님)
변형class-variance-authority
컴포넌트 관례shadcn/ui 형태 (Radix + CVA + 토큰 레이어)
진짜 진입 장벽은 AST가 아니라 scenes.json입니다. wafflebase 자신의 매니페스트는 손으로 쓴 204줄이고, 여기에 providers 모듈과 자기 API 모양에 맞는 fixture가 더 필요합니다. “플러그인 설치하면 됩니다”는 사실이 아닙니다 — 설치와 첫 렌더 사이에 저작이 있습니다. 낯선 앱에서 이게 1시간을 넘기면 문서를 더 쓸 게 아니라 설정 표면을 다시 설계해야 한다는 것이 기준선입니다.

모노레포 밖에 설치해 보는 것은 명령 다섯 줄입니다. npm pack으로 tarball을 만들고, 레포 밖 디렉터리에서 npm install합니다. npm에 배포되어 있지 않습니다. 셋업을 도와주는 스킬이 저장소에 있습니다 — design-sandbox-bringup.

디버그 리포터

  • @wafflebase/debug-report/react를 마운트하고, /plugin을 Vite 플러그인으로 추가합니다.
  • 호스트가 제공하는 것은 둘뿐: 보고할 라우트, 그리고 캔버스 표면이 있다면 locateOnCanvas(점 → 의미 있는 주소). 캔버스가 없으면 두 번째는 생략하고, 캔버스의 모든 점은 리전이 됩니다.
  • React가 없는 호스트는 코어(.)만 쓰고 자기 UI를 그릴 수 있습니다 — 세션, 스토어, 파서, HostAdapter는 프레임워크 무관입니다.
