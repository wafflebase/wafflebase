Retire Figma as the source of truth and put code in its place,

Problem03

The same bottleneck, in two places

A · A design change

What it takes to change one value

A screenshot, a ticket, a developer's schedule, a PR. Whoever noticed it is not whoever fixes it. A designer can get the hover state right and still have no way to hand it over.

B · Something seen on screen

The issue tracker makes the reporter translate

Repro steps, file locations, labels. Translating costs more than noticing. So most observations are never reported at all, and the ones that are arrive after the context is gone.

In both cases what is blocked is not the tooling — it is the translation between an observation and the code.

Premise04

People supply the coordinates and the judgement.
Tools and agents do the translating, verifying and assembling.

Coordinates

Which thing you mean. One click, one drag.

Judgement

Is this right? Does it go out? Nothing ships that a person did not approve.

Translation

File paths, AST nodes, commits, PRs. Every part nobody wants to write.

Design Editor05

Design Editor — open the real screen, edit the real source

  • Renders the app's real routes from the real component source. Not a mockup — what the committed code actually does.
  • The node you click is that JSX node in that file. Change a class, a spacing, a token, and the preview follows immediately.
  • Save writes into your working tree's .tsx and token source. The review screen is git diff.
dev only Vite plugin React 19 · Tailwind v4 · CVA No backend, no DB

Architecture07

Architecture — one bridge, one mutator, two documents

Shell (index.html)The 3-pane editor UI. Prebuilt and served by the middleware — so the consumer's Tailwind can never repaint our panels.
Frame (scene.html)A separate JS realm. The consumer's real components, transformed by the consumer's own Vite, rendered and stamped via ?wbFrame=.
▼   HTTP · /__design-editor/api/*   ▼
plugin/designEditor() · path guard · transactions (undo/redo) · scene registry
server/jsx-nodes · extract · inject · stamp — the AST mutator that reads and writes the source
TokenAdapterThe seam a project's own token pipeline plugs into (swappable)
▼   File writes (anything outside root is refused)   ▼
The consumer's working treeBackups go to node_modules/.cache/. Nothing is ever left beside the source.

Splitting the shell and the frame into two separate documents is the centre of this architecture.
The panels have to be drawn by our CSS, and the thing under review by theirs.

Decision ①08

We dropped hosting

The first design

Hand us a repo URL and we run it

Our infrastructure runs the dev server, an agent makes the fix, we open the PR.

Today

A dev-only Vite plugin on the developer's own machine

Edits land in your own working tree. git diff is the review screen, and the undo of last resort.

  • Every core mechanism in the engine assumes the source tree sits on the same filesystem as the dev server — middleware that reads and writes source, file-path-based module ids, an HMR push after each write, a second HTML entry point.
  • Running that against someone else's repo means checking out their code, installing it and executing it — arbitrary code execution, multi-tenancy, cold starts, npm supply-chain exposure. That is a separate product, not a feature.
Decision ②09

We split it into two packages

PackagePublishedContents
@wafflebase/design-editorpublicVite plugin, AST mutator, bridge protocol, editor shell
packages/design-sandboxprivatewafflebase-only: scene manifest, providers, fixtures, canvas scenes, our token adapter

While both halves live in one package, "does this work in somebody else's repo?" can only be answered by reading. And when we re-checked the coupling list by hand, 2 entries pointed at the wrong place and 5 were missing outright.

  • A mechanical test: the published package has zero @wafflebase/* dependencies. Reverse the direction and the consumer's pnpm install breaks — no reviewer judgement required.
Debug Report10

Debug Reporter — one shortcut, one aim, one sentence

1 · Arm itMod+Shift+Y. An outline follows the pointer.
2 · Capturec to capture / r for a region → one sentence. Collect as many as you like.
3 · Hand overv for the review panel → hand the whole batch over at once.
▼
4 · An agent draftsThe issue text, plus a proposal for how this batch splits into PRs
5 · A person confirmsEdit the sentence, drop an item, regroup. Nothing goes out before it is confirmed.
▼
6 · Verify → landAnything reproducible gets replayed; appearance reports go down the visual lane. A PR, an issue, or a comment on an existing one.
7 · The result comes backIncluding every way the pipeline's output differs from the shape that was approved — in the same panel.

The reporter writes no file paths, no repro steps, no labels. The sentence is the spec, and that same sentence later becomes the "why" in the commit message.

It is not only for bugs. There are eight kinds of item — spacing, color, token, wording, accessibility, small affordances, structure, logic — and an outright bug is one of them. The point of the tool is that every "something's off here" comes in through the same door — there should be no moment where you think well, it's not really a bug and put your hand down.

Try it11

How to try it — two commands and one shortcut

Design editor

pnpm design
→ localhost:5173/__design-editor/
→ edit → Save to Code
pnpm design-pr

What you need: Node 22+, git, and a name and address to commit with. No pnpm services, no Docker, no DB, no backend — scenes answer for their own data with fixtures, which makes this the one part of wafflebase that runs entirely on its own.

Debug reporter

pnpm --filter @wafflebase/frontend dev
→ /harness/hunt?surface=sheet
→ Mod+Shift+Y → c → one sentence
→ v → Hand over

With no drafting key, it hands over your sentence as written, undrafted — one PR per item. The feature does not stop.

In the hands-on session that follows, you'll run both flows end to end once on your own machine. Just follow the separate tutorial page.

Wrap-up12

What we expect, and what's left

Expected

  • A design change's round trip goes from ticket → schedule → PR to click → save → PR.
  • Cheap observation means more reports, and more reports fill the regression lane.
  • Neither tool is wafflebase-specific — one plugin, one package. We actually ran them inside another project.

Honestly, what's left

  • Not published to npm — install from a tarball or as a workspace package.
  • The agent editing loop is unbuilt. The debug reporter is standing in for it.
  • Fork PRs cannot enter the auto-fix loop — an outside contributor's work ends at the issue. A real hole that needs a decision.
  • Reporting from deployed environments (SP2) is deliberately unscheduled. The risk profile changes the moment a screenshot can contain somebody else's document.
  • The setup cliff: authoring the scene manifest + providers + fixtures. The baseline is that if it takes over an hour on an unfamiliar app, we redesign the configuration surface.
  • The name still doesn't fit. In most products debug-report reads as "diagnostic dump", and bug-report pushes seven of the eight kinds above out of the name. Suggestions welcome.
