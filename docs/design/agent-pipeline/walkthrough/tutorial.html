Design Editor · Debug Reporter — How to Run

Run both tools end to end once, on your own machine. Change something on screen and take it all the way to a PR; spot something on screen and take it all the way to a report bundle. Type the commands exactly as written. Every step also tells you what you should see if it worked.

Part AWhat the Design Editor is

It is a dev-only Vite plugin that renders the app's real routes from the real component source, then writes what you change on screen back into the .tsx and token source on your own disk. You are looking at what the committed code does, not at a mockup — and the review screen is git diff.

This tool writes files into your working tree. That is the point of it. Every write that would land outside root is refused, and backups go to node_modules/.cache/wafflebase-design-editor/ rather than next to the source. If you have work in progress, commit or stash it before you start.

Why no backend, database or Docker is needed — the scenes answer their own data requests from fixtures, and any network request that would leave the frame is blocked. This is the only part of wafflebase that runs standalone.

A1. Boot it

  1. One command, from the repository folder

    # from the repository root
pnpm design

# if you don't have pnpm yet — does the same thing, and sets pnpm up too
node scripts/design.mjs

    Why not pnpm --filter … dev — the editor UI (the shell) is served from a prebuilt bundle, not from source. The raw dev command will happily serve you yesterday's shell against today's code. pnpm design compares mtimes, rebuilds only when it has to, and skips every step that is already done.

  2. Read these two lines out of the output

    ✓ dependencies installed ✓ editor shell built ✓ @wafflebase/core built ✓ the design editor is at http://localhost:5173/__design-editor/ [design-editor] editing /home/you/wafflebase — open /__design-editor/ VITE v6.4.3 ready in 551 ms
    CheckThe path after editing is the repository you actually mean to edit. If you have several clones or are using a worktree, stop and confirm it here. Get this wrong and your git diff will look empty later.
    CheckThe port may not be 5173. If something already holds it, Vite takes the next one, and the address it actually printed is the right one.

  3. See at a glance whether your config was picked up

    curl -s localhost:5173/__design-editor/api/health | jq
    { "ok": true, "root": "/home/you/wafflebase", "scenes": ".../packages/design-sandbox/scenes.config.json", "providers": ".../packages/design-sandbox/src/scenes/providers.tsx", "tokens": "configured", "aliases": [{ "find": "@", "replacement": "packages/frontend/src" }, "…"] }

    This is the first place to look when the screen comes up but something feels off. Before you debug a scene, it answers "is my config actually wired in?"

A2. Learn the screen

Left · what you are looking at

Components — a single piece of the design system (a button, a card, a menu). Split into Primitives and App components.

Scenes — a single page of the real app (document list, login, settings). Ten of the eleven mount; pdf-viewer is marked deferred and shows as disabled.

Middle · the real thing

Drag the empty background to pan. Ctrl/⌘+scroll zooms around the pointer.

The buttons along the top: Pick (makes a click inside the frame select instead of act), Mock data (empties the list fixtures so you can see the empty state), viewport width, and refresh.

Right · what you can change

Layout — the structure of what is on screen. Click a row to select that piece; a spacing, size and alignment editor opens beside it.

Bindings (component mode only) — which token each part of this component uses.

Tokens — the values of the tokens themselves. Change one here and everything that uses it follows.

CheckOpen a scene and confirm the left-hand list and the middle of the screen name the same thing. If the preview changes but the page "looks the same", you are usually looking at a different scene than the one you had in mind.

A3. Hands-on — change one class

  1. Open a scene

    In Scenes mode, pick one with clearly separated elements — documents or login work well.

  2. Turn Pick on and click an element inside the frame

    With Pick off, a click actually presses the element (a button gets pressed). Clicking a row in the Layout outline on the right makes the same selection.

    CheckOnce something is selected, a small class editor appears next to that node and the matching row in the right-hand outline is highlighted. If the outline is empty, that scene's file is missing from components in the manifest, so it has no source anchors.

  3. Change a class — a padding or color utility, say

    CheckThe frame updates immediately. Nothing has been written to any file yet. The number next to Save to Code in the header goes up by one.

    If the preview picks up no styling at all — a class assembled at runtime produces no rule unless Tailwind's scan saw it. The editor registers these candidates, but a class that gets rejected or hits the cap has no rule behind it and renders as nothing visible.

  4. Undo the staged edits with ⌘/Ctrl+Z and ⇧+⌘/Ctrl+Z

    Edits made before a save pile up on a stack. Undo / Redo / Reset in the header drive the same stack.

A4. Hands-on — change a token value

  1. Go to the Tokens tab on the right

    Colors are tokens, not classes — each has a name like primary, and which part uses which name is already decided.

  2. Change one token's value

    CheckEverything that uses that token moves at once. If only one element changed, you changed that element's class, not a token.

    Why the preview is the real thing — wafflebase's tokens live in TypeScript consts, and the CSS the app uses is generated. So the preview takes the patched source text and runs the real emitter over it to build the variable map. Keeping the preview from diverging from what a save would write is the entire reason that worker exists.

  3. Toggle light and dark

    Use the Dark button in the header. For a token with separate per-theme values, only one side changing is correct.

A5. Save to code

  1. Press Save to Code in the header

    The button shows how many changes are staged. Pressing it opens a review — how it looks now beside how it will look, and under that, the exact lines that will change in each file.

  2. Approve

    CheckNothing is written before you approve. Once you do, the changes land in the repository files on your own machine and go nowhere else.

  3. Confirm where it wrote, in two places

    • The write log (the scroll icon in the header, with a count beside it) — everything written this session, newest first, down to which file it landed in. The toast that appears on save disappears; this does not.
    • The ⓘ button — Editing, the folder the editor writes to. With several clones around, this is the authority.

  4. Confirm it in the terminal

    git diff

    Color changes usually land in packages/core/src/tokens/; a change confined to one component lands in that component's file.

    If git diff is empty, you are almost certainly looking at a different clone. Press ⓘ in the editor header, read the Editing path, and check again from that folder.
Leave the editor running as you move to the next step. The PR script reads the record of "what was written" that the running server holds. You can still create a PR after closing it, but the commit then widens to your whole working tree and the description gets less accurate.

A6. Open a PR

  1. In a second terminal, from the same folder

    # shows only what it would do, and changes nothing
pnpm design-pr --dry-run

# for real
pnpm design-pr

    It prints the branch it will create, the files it will commit and the title, then proceeds. It commits only the files the editor changed — any other work in progress is listed and left alone.

  2. The script works out which path your setup is on

    ConditionResult
    rung 3GitHub CLI + push accessBranch, commit, push and PR, all of it. Prints the URL and opens the browser.
    rung 2GitHub CLI, no push accessMost of you will be here. Creates a fork, pushes there, and opens a PR against the original (it asks for confirmation the first time).
    rung 1No GitHub CLIPushes the branch and opens GitHub's compare page in the browser — a pre-filled form, so all that is left is the green button.
    rung 0No git / no originSays so and stops. Get the code with git clone, not as a copied folder.

    Why rung 1 exists — assume gh auth login and the very people this tool exists for (designers who do not write code) stop on the first step. There has to be a path that needs nothing but a browser.

  3. If you want a better description

    The default description is pulled from the editor's own edit log: accurate, but dry. If you have Claude Code:

    Open a PR for my design changes

    It reads the same log and the real diff, writes a title and body, and hands them to the same script. You can also supply them yourself:

    pnpm design-pr --title "Soften the primary button's hover" --body-file notes.md

What it never does (a guarantee, not a convention)

  • It never commits to main — it always creates a branch.
  • It never commits a file the editor did not change.
  • It never force-pushes and never overwrites an existing branch.
  • It never stores or asks for a password or token. git and gh run as you, with the credentials already on your machine.

A7. Undo

  • Before a save — ⌘/Ctrl+Z in the editor, or Reset in the header.
  • After a save, before the PR — read the file list out of the write log and run git checkout -- <file>. Or use the editor's Undo, which reverts the file through the bridge.
  • To finish the exercise clean — run git status, see what is left over, and clear it. Backups live in node_modules/.cache/, not next to the source, so they never dirty the repository.

Part BWhat the Debug Reporter is

It is a dev-only reporting overlay that sits on top of the running app. Press a shortcut, point at what is wrong, say it in one sentence, collect a few, and hand them over in one batch. An agent drafts the issue text and proposes how the batch splits into PRs; only after a person confirms does the pipeline verify it and land it.

What the person does

Point, write one sentence, and judge — fix the wording, drop an item, adjust the grouping, confirm.

What the person does not do

File paths, repro steps, labels. That one sentence goes on to become the "why" in the commit message, verbatim.

What the pipeline does not do

It opens nothing on its own. None of the intake scripts creates a branch, a commit, an issue or a PR.

This is not only for bugs. An item is one of eight kinds — spacing, color, token, copy, a11y, affordance, layout, logic — and an outright bug is just the one, logic. "This gap looks a bit tight", "this wording reads oddly", "there should be a button here" are all perfectly normal reports. Look for that sort of thing in the exercise too — if you think you have to find a bug, nobody finds anything.

In production it does not exist at all — the mount is statically replaced by import.meta.env.DEV, so the code never enters the shipped bundle. It is absent, not disabled.

Optional — a drafting key

For the agent to write drafts, the dev server process has to be able to see a credential (ANTHROPIC_API_KEY, ANTHROPIC_AUTH_TOKEN, or ant auth login). The whole exercise works without one — your sentence is handed over as written, with no draft, and you get one PR per item.

The key never reaches the browser. Drafting is a dev-server endpoint, and the request carries no tools parameter at all — it is output-only. The scene frame is where app code runs, so a key readable from there is a key exposed to every dependency.

B2. Turn it on

Mod+Shift+Y toggle debug mode c capture r region drag v review panel Esc peel off one layer
CheckThe floating badge reads c capture · r region · v review · Esc, and an outline follows your pointer at all times. The badge is the authority on the current bindings.

Why Mod+Shift+Y — it is the combination that avoids both the engines' own shortcut catalogues and everything the browser reserves. It is also the only binding that has to work while debug mode is off, which is why it is the only one with modifiers. The rest are single keys that respond only while the mode is on, and if a text field has focus, the field takes the keyboard.

B3. Hands-on — aim at a DOM target

  1. Put the pointer over a button on /login or in the header

  2. Press c — do not click

    CheckEven with the pointer over an icon, it captures the button, not the icon's <svg>. Pointing at a control means you meant that control, so it promotes to the nearest meaningful ancestor.

  3. Write one sentence and press Enter

    For example: "The horizontal padding on this button looks tighter than on the one next to it." You write no file, and no repro steps.

    CheckThe count on the badge goes up by one. DOM targets are not photographed — they are described by selector, box and a text excerpt. That is what the agent greps the source with.

B4. Hands-on — aim at a canvas target

  1. Go to /harness/hunt?surface=sheet and put the pointer over a cell

  2. Press c

    CheckThe target comes out as a meaningful address — Sheet1!C7, say. Not a 1280×721 photograph of the whole sheet.
    CheckThe captured image contains both the grid and the selection markers.

This is the reason the tool exists. The accessibility tree cannot see inside a canvas, and hit-testing gives no answer either — both sheet canvases are pointer-events: none and the wrapping div handles the events, so in the middle of the grid elementsFromPoint returns four divs and zero canvases. So the locator queries the DOM to find the canvas, then asks the mounted engine which cell it is. When the engine locator cannot answer, it falls back to a small region around the cursor rather than photographing the whole container.

B5. Hands-on — report a state that disappears

  1. Hover somewhere a tooltip appears, or open a dropdown and leave it open.

  2. Press c without moving the pointer

    CheckThe tooltip is captured while it is still alive. The sentence box opens after the capture is done, so it does not matter if the state collapses afterwards.

This is why the trigger is a key and not a click. Hover tooltips, open menus and drags in progress are destroyed by the very click that pointing would require. On top of that, an overlay that intercepts pointer events stops the app underneath from tracking hover and from seeing the mouseup of a drag in progress. So while idle the overlay observes the pointer passively only (no preventDefault, no stopPropagation) and intercepts keys alone, in the capture phase. A key does not move the pointer.

The limitation that remains — you still cannot aim at a tooltip drawn away from the cursor, because moving the pointer there is what dismisses it. The only answer is to freeze the frame and aim inside it, and on a screen with DPR 2 and 12 canvases that is not cheap, so it is on hold.

B6. Hands-on — the region drag

  1. Go to /harness/docs (12 canvases stacked vertically)

  2. Press r and drag across a page seam

    CheckThe bottom of the captured image is not black. It composites every canvas the rectangle intersects — pick by which one contains the center instead, and the person reporting a seam ends up attaching evidence with the seam missing.

  3. Try the same r drag on a screen with zero canvases, like /login

    CheckYou get more than coordinates — it records a list of the meaningful elements the rectangle intersects (selector plus text excerpt).

B7. Hands-on — what cancel discards

This step lets you see one of the tool's rules for yourself. A tool that loses reports is worse than no tool at all — the reporter believes it was filed, and never makes the next observation.

  1. Press Esc while typing the sentence

    CheckOnly that item is discarded; debug mode stays on. You return to aiming.

  2. Try to save with an empty sentence

    CheckThe save control is visibly disabled and says why. It never swallows the report silently and drops it.

  3. Keep pressing Esc

    It peels off one layer at a time: panel → pending item → region mode → debug mode. It does not close everything at once, so that one key cannot destroy work you did not know was about to vanish.

B8. The review panel

Once you have three or four, press v to open the Debug reports panel.

  • Fix the sentences and titles. With a drafting key, the agent's draft is already filled in; without one, your own sentence is. Either way it is an editable draft and you are the author.
  • The thumbnails are the consent gate. Every image that will leave is shown here.
  • Three dispositions — Verify (replay it; if it holds, a PR) · File it (an issue, no replay) · Drop (this one is not going out).
  • The agent:candidate checkbox records intent. The automated-contribution gate requires a non-bot author, so a label alone never opens it — which is why this checkbox does not weaken the gate.
  • Proposed pull requests — detach an item from a proposed group, split a PR, merge two. File names never appear in the UI. Merging across kinds is warned about, not blocked.

What gets grouped together — the criterion is homogeneity, not count. Two padding fixes pass or fail together; a padding fix and a formula-engine bug do not. So spacing, color, token, copy and a11y group with their own kind, layout only within the same file, and logic is never grouped — there is no reason for one blocked item to hold the rest hostage. One item is one commit, so a reviewer can reject a single report by dropping a single commit.

B9. Hand over

  1. Hand over N report(s), at the bottom of the panel

    CheckIf any sentence is still empty the button is disabled and tells you how many are blank. You can hand over while drafts are still pending — the model is not a dependency.

  2. Confirm it on disk

    ls .wb-reports/
cat .wb-reports/<session>/bundle.json | jq '.items[] | {note, target: .target.kind}'

    Capture images are stored as separate files beside the bundle — the bundle has to stay small and the images run to megabytes.

    CheckHand over twice in one session and bundle-2.json appears next to bundle.json. Nothing is overwritten — saying it was sent and then erasing the earlier batch is the failure this feature most wants to avoid.

B10. Intake — what happens to the batch

In the session we run only step 1 by hand and skim the rest from the table. None of these scripts opens a PR or an issue on its own.

DIR=.wb-reports/<session>

# 1. Reject a bundle that cannot be acted on. From the next step on, commits can be made.
node ./scripts/agent/report-bundle.mjs "$DIR" --check

If you use Claude Code, the whole flow is one command:

/report-intake            # defaults to the newest directory under .wb-reports/
StageWhat it doesWhat it does not do
report-bundleReads and validates the bundle, fail-closedDoes not repair anything — a bundle it does not understand is rejected
report-priorReads the repo's open issues as prior reportsNo judgement, no writes
report-intakeMasks secrets, decides duplicates, routes destinations, produces a planExecutes nothing, files nothing. A destination is not a deletion
report-verifyWorks out what verification means for each itemDoes not run the lanes itself (they need a browser and Docker)
report-to-prAssembles PRs, forces splits and merges, records the deltasStarts no processes at all
report-backWrites the outcome beside the bundle — including the reason for every adjustmentDoes not interpret it

Two things worth watching here

  • A proposal is not a contract. The browser does not know which files will change. So it is adjusted in exactly two directions — overlapping files force a merge (transitively: if A–B overlap and B–C overlap, all three become one PR), and a misjudged kind forces a split. Splitting is always safe; merging is not. And an adjustment is never silent — the result comes back as "proposed 2 PRs → actually 3 (…reason…)".
  • A failed verification never deletes a report. "Did not reproduce" does not mean "the observation was wrong", so it only lowers the destination — the expectation and the failed replay go into an issue together, so a person, not a machine, looks at the discrepancy.

Why duplicate detection uses two different measures — a report is one sentence; an issue body is several paragraphs. Under containment, a long issue merely happening to contain the short sentence's words scores 1.0, and a perfectly good report vanishes as a comment on the wrong issue. So report↔issue uses Dice, and report↔ledger uses containment.

Adding it to your own project

Not part of the session exercise, but this is where most of the questions come from.

Design Editor

// the consumer's vite.config.ts
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'
import { designEditor, cssVariables } from '@wafflebase/design-editor'

export default defineConfig({
  plugins: [
    react(),
    designEditor({
      root:      process.cwd(),         // the write boundary — nothing is written outside it
      scenes:    'design/scenes.json',  // which routes are editable
      providers: 'design/providers.tsx',
      tokens:    cssVariables({ stylesheet: 'src/index.css' }),
    }),
  ],
})
Support matrix
BundlerVite 6+ (dev server only)
FrameworkReact 19, JSX/TSX source
StylingTailwind v4 (required for class editing; not required if you only edit tokens)
Variantsclass-variance-authority
Component conventionshadcn/ui shape (Radix + CVA + a token layer)
The real barrier to entry is scenes.json, not the AST. wafflebase's own manifest is 204 hand-written lines, and on top of that you need a providers module and fixtures shaped like your own API. "Just install the plugin" is not true — between installing and the first render there is authoring. The baseline is this: if that takes more than an hour on an unfamiliar app, the answer is not more documentation, it is that the configuration surface needs redesigning.

Trying it outside the monorepo is five commands. Build a tarball with npm pack, then npm install it from a directory outside the repo. It is not published to npm. There is a skill in the repository that helps with setup — design-sandbox-bringup.

Debug Reporter

  • Mount @wafflebase/debug-report/react and add /plugin as a Vite plugin.
  • The host supplies two things only: the routes to report on, and — if it has canvas surfaces — locateOnCanvas (a point → a meaningful address). With no canvases, drop the second one and every point on a canvas becomes a region.
  • A host without React can use the core (.) alone and draw its own UI — the session, the store, the parser and HostAdapter are framework-agnostic.
